# 로컬 LLM 상성 코치 — 데이터/컨텍스트 설계

> 상태: CLI 프로토타입 (Ollama). web-llm 브라우저 탑재은 8장 이후 단계.

## 1. 목표

"아트록스로 피오라를 상대하면?" 같은 질문에 아래 항목을 근거와 함께 답한다.

상성 한 줄 요약 · 라인전 구도 · 시작 아이템 · 첫 아이템 · 최종 아이템 · 룬 · 소환사 주문 ·
조심할 스킬 · 콤보와 플레이 팁. 나중에는 양 팀 조합을 넣으면 메타에 맞는 챔피언 추천까지.

소형 모델(gemma4:e2b, 브라우저 탑재 후보)은 **추론기가 아니라 서술기**로 쓴다. 결론은 코드와 지식이
정하고, 모델은 근거를 엮어 문장으로 풀어내는 역할만 맡는다. 이 판단은 5장의 측정에서 나왔다.

## 2. 컨텍스트 4계층

| 계층 | 출처 | 생성 방식 | 예시 | 코드 |
|---|---|---|---|---|
| A. 사실 카드 | `champions-normalized-*.json` + ddragon 보조 | 빌드 시 결정적 계산 | "아트록스 방어력 38, 전체 중 상위 6%", "피오라 W: 마법 피해, 계수 주문력 100%, 효과 기절" | `lib/facts.ts` |
| B. 후보 선별 | items / runes / summoner normalized | 질의 시 규칙 기반 retrieval | 상대 계수가 AD → 방어력 아이템만 티어별로, 상대에게 회복이 있으면 치유 감소 목록 | `lib/retrieval.ts` |
| C. 지식 계층 | `knowledge/playbooks/*.json`, `knowledge/tips/*.json` | 사람이 작성, 조건으로 선택 | 콤보 "Q 1타 → E → 평타 → W → Q 2·3타", "응수가 살아 있으면 W를 아낀다" | `lib/playbook.ts`, `lib/knowledge.ts` |
| D. 결론 조립 | A+B+C | 코드가 문장·목록으로 확정 | "우선 올릴 방어 스탯은 방어력", "룬: 정복자, 최후의 저항" | `lib/prompt.ts` |

D 계층이 이 설계의 핵심이다. 소형 모델에게 후보 목록을 주고 고르라고 하면 엉뚱한 아이템을 집는다.
고르는 일은 코드가 하고 모델에게는 이미 정해진 이름과 그 근거만 넘긴다.

### 사용자 예시 문장을 계층으로 분해

| 문장 | 계층 |
|---|---|
| 오공의 마법 저항력은 낮은 편 | A (백분위 하위 5%) |
| 시작 아이템은 도란의 투구 | B (시작 아이템 중 마법 저항력 보유 유일) + C |
| 럼블 E 작살은 마법 저항력을 낮춘다 | A (툴팁 효과 태그) |
| 마법 저항력 먼저: 헤르메스 / 주문포식자 / 망령의 두건 | C (`refs.items`) → D |
| 정복자보다 착취 | C (`refs.runes` + `avoid.runes`) |
| 점화보다 순간이동 | C (동일) |
| 아트록스 콤보 Q 1타 → E → 평타 → W → Q 2·3타 | C (플레이북 `combo`) |
| 피오라가 유리한 구도 | C (`category: verdict`) |

## 3. 사실 카드(A)

`npm run llm:build` → `public/data/<patch>/llm/champion-cards-ko_KR.json` (173 챔피언, 약 1 MB)

- 정체: 이름, 역할 태그, 근접/원거리와 사거리, 자원
- 스탯: 1·6·11·18 레벨 값과 **전체 챔피언 대비 백분위·5단계 등급**
  (성장 공식 `base + growth × (L−1) × (0.7025 + 0.0175 × (L−1))`)
- 피해 프로필: 툴팁의 물리/마법/고정 피해 문구 집계 → 주 피해 유형
- **계수 프로필**: 툴팁의 "(105% 주문력)", "(50% 추가 공격력)", "최대 체력의 8%" 를 스탯별 최대값으로 수집.
  865개 스킬 중 주문력 465, 추가 공격력 179, 공격력 102, 체력 273개가 잡힌다.
  피해 유형이 혼합인 챔피언(피오라: 물리1·마법1·고정2)의 방어 대응을 계수로 결정한다.
- 스킬별: 슬롯·이름·요약·툴팁 평문·쿨타임(1랭크 포함)·비용·피해 유형·계수·효과 태그
- 효과 태그 32종: 적 마법 저항력 감소, 적 방어력 감소, 둔화, 기절, 에어본, 침묵, 보호막, 회복,
  은신, 이동기, 최대 체력 비례, 고정 피해, 처형, 피해 면역, 투사체 차단 등
- 공식 allytips / enemytips

빌드 시 태그 빈도를 출력해 정규식 오탐을 눈으로 검수한다(럼블 E "감소 효과가 50% 증가"가
"자기 마법 저항력 증가"로 잡히던 오탐을 이렇게 발견해 고쳤다).

## 4. 지식 계층(C) 스키마

`knowledge/playbooks/<ChampionId>.json` — 챔피언 단위. 상성마다 쓰지 않는다.

```json
{
  "id": "aatrox-rune-default",
  "category": "rune",
  "text": "핵심 룬은 정복자가 기본이다. … 최후의 일격보다 최후의 저항이 무난하다.",
  "when": { "enemyRange": ["원거리"] },
  "refs": { "runes": ["정복자", "최후의 저항"] },
  "avoid": { "runes": ["최후의 일격"] },
  "source": "…",
  "verifiedPatch": "26.17"
}
```

- `category`: `combo` `phase` `rune` `summoner` `start-item` `first-item` `core-item`
  `situational-item` `laning` `teamfight` `skill`
- `when`: 상대 카드의 파생 사실로 판정한다. `enemyDamage` `enemyScaling` `enemyRange`
  `enemyHasEffects` `enemyLacksEffects` `enemyRoles` `enemyIds` `lanes`.
  덕분에 "상대가 원거리면 재생의 바람" 같은 조건부 지식을 챔피언당 한 번만 쓰면 된다.
- `refs` / `avoid`: 본문이 권장하는 이름과 비교 대상으로만 언급한 이름. **자유 텍스트에서 이름을
  추출하지 않는다.** 작성자가 명시하고 검증기가 데이터와 대조한다.
- `playing` / `against` 두 묶음. 상대 플레이북의 `against` 를 가져와 "상대 대응" 지식으로 쓴다.

`knowledge/tips/<ChampionId>.json` — 상성 한정 지식. `vs`, `lane` 으로 좁힌다.
`category: verdict` 는 상성 판정(누가 유리한지)이며, 데이터로 도출할 수 없어 반드시 사람이 쓴다.

## 5. 결론 조립(D)

`lib/prompt.ts` 가 두 블록을 만든다.

**자동 결론** — A+B 에서 확정되는 사실을 문장으로. 예: 피오라전에서

```
- 상대 피오라의 피해 유형은 혼합이지만 계수 프로필이 AD이므로 내가 우선 올릴 방어 스탯은 방어력이다.
- 상대는 고정 피해 스킬(P 치명적인 검무, R 대결투)을 갖고 있어 방어력·마법 저항력으로 줄일 수 없다.
- 상대 군중 제어 스킬: W 응수(기절).
- 내 최장 기본 스킬 쿨타임은 W 지옥사슬 20초, 상대는 W 응수 24초다(1레벨 기준).
```

**권장안 초안** — 항목별 선택을 확정한 목록. C 의 `refs` 에서 모으고 `avoid` 를 뺀다.
팁(상성 한정)이 플레이북(챔피언 단위)보다 앞선다.

```
- 상성 판정: 피오라 쪽이 유리한 구도다. …
- 시작 아이템: 도란의 방패, 도란의 검
- 첫 아이템 후보: 처형인의 대검, 판금 장화
- 코어 아이템: 칠흑의 양날 도끼, 죽음의 무도, 스테락의 도전, 수호 천사, 맬모셔스의 아귀
- 룬: 정복자, 최후의 저항
- 소환사 주문: 점멸, 순간이동, 점화
```

지식 카드가 지목한 아이템은 후보 목록에도 고정 포함한다(`pinned`). 가격 오름차순 절단 때문에
아트록스 코어(칠흑의 양날 도끼 3000G, 죽음의 무도 3300G)가 목록에서 잘려 나가던 문제를 이렇게 막았다.
아군 보조 아이템(`Aura`, `GoldPer` 태그)은 1대1 조언에 부적합하므로 후보에서 제외한다.

## 6. 검증 (`npm run llm:validate`)

지식 계층이 데이터와 어긋나는 것을 CI 에서 잡는다.

1. 참조하는 챔피언 id 존재 여부
2. `refs` / `avoid` 의 아이템·룬·소환사 주문 이름이 현재 패치에 존재하는지.
   **협곡에서 구매 가능한 아이템만 유효**로 본다(아레나 전용 "닌자의 신발" 같은 이름을 걸러낸다)
3. `refs` 에 적은 이름이 본문에도 실제로 등장하는지
4. `when` 의 효과 태그가 실제로 생성되는 태그인지
5. `refs` 와 `avoid` 에 같은 이름이 동시에 있는지

가짜 항목(존재하지 않는 룬 이름, 다른 모드 전용 아이템)을 넣어 검증기가 잡는지 확인했다.

## 7. 측정 (2026-09-04, M2 Pro 32GB, Ollama 0.33)

### 아트록스 vs 피오라 (답지 없이 웹 검색으로만 지식 작성, 기대 그룹 8개)

| 모델 | 컨텍스트 | 적중 | 프롬프트 | 생성 속도 | 소요 |
|---|---|---|---|---|---|
| gemma4:e2b | 지식 없음 (A+B+자동 결론만) | 1/8 | 7.0k tok | 61 tok/s | 18s |
| gemma4:e2b | 지식 + 권장안 초안 | 7/8 | 8.9k tok | 59 tok/s | 30s |
| gemma4:e2b | compact + 지식 + 권장안 | 7/8 | 6.2k tok | 58 tok/s | 17s |
| gemma4:12b | 지식 없음 | 3/8 | 7.0k tok | 17 tok/s | 90s |
| gemma4:12b | 지식 + 권장안 초안 | 8/8 | 8.6k tok | 16 tok/s | 120s |
| gemma4:12b | compact + 지식 + 권장안 | 7/8 | 5.9k tok | 16 tok/s | 80s |

권장안 초안을 넣기 전 e2b 는 5/8 이었고 "최종 아이템: 처형인의 대검", "룬: 정복자, 착취의 손아귀, 여진"
처럼 후보 목록에서 아무 이름이나 집었다. 초안을 넣은 뒤 아이템·룬·소환사 주문·콤보가 모두 정확해졌다.
상성 판정은 초안에 넣기 전까지 e2b 가 "아트록스가 유리"로 뒤집었다. `verdict` 팁을 추가해 해결했다.

### 오공 vs 럼블 (사용자가 답지를 준 케이스, 기대 그룹 6개)

| 모델 | 컨텍스트 | 적중 |
|---|---|---|
| gemma4:e2b | 팁 포함 | 6/6 |
| gemma4:e2b | 팁 제외 | 2/6 |
| gemma4:12b | 팁 포함 | 6/6 |
| gemma4:12b | 팁 제외 | 4/6 |

### 프롬프트 프로필과 스트리밍 체감 (동일 케이스)

CLI 는 처음부터 스트리밍이다(`/api/chat` 의 `stream: true`, 토큰을 받는 즉시 출력).
따라서 체감 대기 시간은 생성 속도가 아니라 **첫 토큰까지 걸리는 시간**이 결정하고, 그 대부분은 prefill 이다.

| 모델 | 프로필 | 프롬프트 | 첫 토큰까지 | 생성 속도 | 총 |
|---|---|---|---|---|---|
| gemma4:e2b | web | 3438 tok | 4.8s (모델 최초 적재 시) | 64 tok/s | 12s |
| gemma4:e2b | compact | 6177 tok | 9.9s | 60 tok/s | 23s |
| gemma4:12b | web | 3442 tok | 28.6s | 17 tok/s | 67s |
| gemma4:12b | compact | 6181 tok | 44.5s | 17 tok/s | 80s |

프롬프트를 절반으로 줄이면 첫 토큰까지 시간도 대략 절반이 된다. 같은 대화를 반복하면 ollama
프리픽스 캐시가 걸려 0.1초 수준으로 떨어지지만, 실제 사용은 매번 다른 매치업이므로 위 값이 기준이다.

`web` 프로필은 web-llm 용 4k 컨텍스트 예산에 맞춘 것으로, 후보 목록·룬 목록·공식 팁을 빼고
스킬은 한 줄 메타(슬롯·쿨타임·피해 유형·계수·효과)만 남긴다. 적중률은 compact 와 같았다(7/8).

### 관찰

- **지식 계층 없이는 두 모델 모두 실패한다.** e2b 는 존재하는 이름을 엉뚱하게 조합하고,
  12b 는 스탯·스킬 기반 결론은 맞추지만 룬·소환사 주문·콤보는 못 맞춘다.
- **권장안 초안이 있으면 e2b 가 12b 를 거의 따라잡는다.** 두 모델의 차이는 서술 품질과
  라인전 구도 설명의 깊이로 좁혀진다. e2b 는 3.5배 빠르다.
- **compact 모드(툴팁 상세 제거)는 30% 절감에 적중률 손실 0~1개.** 브라우저 기본값으로 적합하다.
- 자유 텍스트 대신 `refs` 로 이름을 구조화한 덕에, 패치로 아이템이 사라지면 검증기가 먼저 잡는다.

## 8. web-llm 탑재 계획

### 모델은 E2B 로 확정

로컬에서 쓰는 `gemma4:e2b` 가 곧 `google/gemma-4-E2B` 다. 총 5.1B, per-layer embedding 으로
**실효 2.3B**, Apache 2.0, 온디바이스 지향. 12b(7.6GB)는 브라우저에서 현실적이지 않으므로
**런타임 모델은 E2B, 12b 는 지식 초안 생성용 오프라인 도구**로 역할을 나눈다.

### 아직 공식 지원이 아니다

`@mlc-ai/web-llm` 최신은 0.2.84 이고, 내장 모델 목록(`prebuiltAppConfig`)에 Gemma 4 가 없다.
mlc-ai/web-llm 이슈 #810 "[Model Request] Gemma 4" 가 열려 있는 상태다. 따라서 세 경로 중 하나를 골라야 한다.

| 경로 | 내용 | 위험 |
|---|---|---|
| A. 커뮤니티 MLC 산출물 | `welcoma/gemma-4-E2B-it-q4f16_1-MLC` (2026-04-14) | 비공식, 다운로드 0회. **컨텍스트 4096** 제약 |
| B. 직접 빌드 | `mlc_llm convert_weight` + `gen_config` 로 q4f16_1 + WebGPU wasm 생성 | 툴체인 구축 필요. 컨텍스트를 8192 로 올릴 수 있음 |
| C. LiteRT-LM 웹 | `gemma-4-E2B-it-web.task` + Chrome WebGPU | web-llm 이 아닌 별도 런타임 |

A 경로의 실제 수치(HF API 조회): 파일 54개 **총 2552 MB**, WebGPU wasm 8.8 MB,
tokenizer 30.7 MB, `context_window_size: 4096`, `prefill_chunk_size: 1024`.

```js
// A 경로 등록 예시 (공식 목록에 없으므로 appConfig 로 직접 등록)
const appConfig = {
  model_list: [{
    model: "https://huggingface.co/welcoma/gemma-4-E2B-it-q4f16_1-MLC",
    model_id: "gemma-4-E2B-it-q4f16_1-MLC",
    model_lib: "https://huggingface.co/welcoma/gemma-4-E2B-it-q4f16_1-MLC/resolve/main/libs/gemma-4-E2B-it-q4f16_1-MLC-webgpu.wasm",
    required_features: ["shader-f16"],
  }],
};
```

### 4k 를 맞추는 방법: 산출물을 성질로 나눈다 (`--split`)

한 번에 모든 소제목을 요구하면 프롬프트가 상한에 붙는다. 산출물을 셋으로 나눈다.

| 구간 | 만드는 주체 | 프롬프트 |
|---|---|---|
| 상성 판정, 시작·첫·최종 아이템, 룬, 소환사 주문, 치유 감소 | **코드** (`renderDecidedSections`) | 0 |
| 선택 이유 (항목별 1~2문장) | LLM 1회 | 1135 tok |
| 라인전 구도, 조심할 스킬, 콤보와 플레이 팁 | LLM 1회 | 2712 tok |

컨텍스트 상한을 결정하는 값은 **호출당 최대 프롬프트**이므로 2712 토큰이 기준이 된다.
단일 호출(3603 토큰)보다 900 토큰 여유가 생기고, 지식 카드가 두 배로 늘어도 4096 안에 들어간다.

이름 목록은 코드가 이미 화면에 렌더링하므로 첫 호출에는 "이름을 다시 나열하지 말고 이유만 쓰라"고 지시한다.
UI 는 확정 목록을 즉시 그리고(모델 적재 전에도 표시 가능) 이유가 도착하면 항목 아래에 붙인다.

| 모델 | 방식 | 적중 | 호출당 최대 프롬프트 | 첫 토큰까지 | 총 |
|---|---|---|---|---|---|
| gemma4:e2b | split (2회) | 8/8 | 2712 tok | 3.5s | 13s |
| gemma4:e2b | 단일 web | 8/8 | 3603 tok | 5.0s | 16s |
| gemma4:12b | split (2회) | 8/8 | 2716 tok | 17.7s | 66s |
| gemma4:12b | 단일 web | 8/8 | 3607 tok | 24.0s | 67s |

분할해도 총 시간은 거의 같다. prefill 이 두 번으로 쪼개질 뿐 총량이 비슷하기 때문이다.
대신 첫 화면이 빨라지고(작은 호출이 먼저 끝난다) 컨텍스트 여유가 생긴다.

### 병렬 호출은 답이 아니다

web-llm 의 `MLCEngine` 은 한 인스턴스에 동시 요청을 받지 못한다. `await` 없이 두 번 호출하면
두 응답의 토큰이 문자 단위로 섞여 나온다(mlc-ai/web-llm 이슈 #522, "Support concurrent requests to
a single model instance"). 서버판 MLC-LLM 에 있는 연속 배칭·요청 스케줄러가 브라우저 빌드에는 없다.
엔진을 두 개 띄우면 되지만 가중치가 VRAM 에 두 번 올라가므로(2.5 GB × 2) 현실적이지 않다.
GPU 디코드가 병목이라 진짜 병렬이 됐다 해도 총 시간은 거의 줄지 않는다.

따라서 **직렬 큐로 처리하고, 줄일 것은 프롬프트 크기와 첫 화면까지의 시간**이다.

### 연속 대화(`--chain`)로 prefill 을 한 번만 낼 수도 있다

같은 대화를 이어가면 첫 턴의 KV 캐시가 남아 두 번째 턴은 질문 문장만 prefill 한다. 실측:

| 방식 | 1턴 prefill | 2턴 prefill | 호출당 최대 컨텍스트 | 비고 |
|---|---|---|---|---|
| `--split` (자료를 두 번 실음) | 1135 tok | 2712 tok | 2712 tok | 여유 1.4k |
| `--chain` (대화 이어가기) | 3483 tok / 4.8s | **0.3s** (캐시 재사용) | 3798 tok 누적 | 여유 0.3k |

chain 은 prefill 총량이 적지만 컨텍스트에 1턴 답변이 쌓여 4096 에 붙는다. 실제로 이 방식에서
2턴 출력이 내부 우선순위 문구를 그대로 복사하고 소제목 형식을 잃는 열화가 관찰됐다.
**web 기본값은 `--split`** 로 두고, 컨텍스트를 8192 로 올린 뒤에 chain 을 재검토한다.

### 사전 생성을 CI 에서 돌릴 수 있다

이 저장소는 공개이므로 **표준 GitHub 호스팅 러너의 실행 시간은 무료·무제한**이다
(GitHub Actions 과금 문서: 공개 저장소와 자체 호스팅 러너는 무료). 신경 쓸 한도는 셋이다.

| 항목 | 값 | 대응 |
|---|---|---|
| 캐시 | 저장소당 10 GB | ollama 모델(약 6.7 GB) 하나만 캐시 |
| 잡 실행 시간 | 잡당 6시간 | 매트릭스 `--shard i/n` 으로 분할, `timeout-minutes: 90` |
| 러너 사양 | 4 vCPU / 16 GB, GPU 없음 | CPU 추론. 메모리 사용 6.7 GB 로 들어감 |

CPU 추론 실측(M2 Pro, GPU 끄고 `ollama ps` 로 100% CPU 확인): prefill 207 tok/s, 생성 47.7 tok/s.
GitHub 러너는 코어 수와 메모리 대역폭이 낮아 3~5배 느릴 것으로 보면 매치업 하나에 약 2분이다.

워크플로: `.github/workflows/llm-precompute.yml` (수동 실행 + 작업 브랜치 push).
기본값을 `--limit 1` 로 두어 스모크 테스트가 가볍게 끝나게 했다. 결과는 artifact 로 올리고,
`commit` 입력을 켤 때만 저장소에 커밋한다.

생성기: `npm run llm:batch`. 지식 카드가 없는 조합은 생성하지 않고(품질이 떨어지므로) 건너뛴다.
생성 후 협곡에서 구매할 수 없는 아이템이 언급되면 잡을 실패시킨다.

로컬(GPU) 실측 3건: 매치업당 8~15초, 호출당 최대 프롬프트 2252~2747 토큰.

### 자주 나오는 상성은 미리 만들어 둔다

가장 큰 체감 개선은 모델을 빠르게 만드는 것이 아니라 **모델을 돌리지 않는 것**이다.
인기 매치업 수백 개는 빌드 시 `gemma4:12b`(또는 더 큰 모델)로 답을 만들어 JSON 으로 배포하면,
브라우저는 2.5 GB 다운로드 없이 즉시 결과를 보여준다. 로컬 모델은 목록에 없는 조합에만 쓴다.
`llm:eval` 의 케이스 파일을 그대로 배치 생성기로 쓸 수 있다.

### 조심할 스킬도 코드가 순위를 정한다

소형 모델은 "무엇이 가장 위험한가"를 실행마다 다르게 골랐다(피오라 W 응수 대신 패시브를 집는 식).
효과 태그에 가중치를 매겨 순위를 계산하고 이유 문구까지 넘긴다(`deriveThreatOrder`).

```
1순위 W 응수 — 공격 무효화: 내 핵심 스킬을 통째로 무효화하고 반격까지 나온다 / 기절: 행동 불가로 이어져 콤보를 전부 받게 된다
2순위 R 대결투 — 고정 피해: 방어력과 마법 저항력으로 줄일 수 없다 / 최대 체력 비례 피해: 체력을 올려도 피해가 함께 커진다
3순위 P 치명적인 검무 — 고정 피해: … / 최대 체력 비례 피해: …
```

가중치 순서는 방어 무력화(저항 감소) → 공격 무효화 → 하드 CC → 고정 피해·체력 비례 → 둔화다.
이 순위를 넣은 뒤 두 모델 모두 8/8 로 올라갔다.

### 단일 호출로 갈 때의 예산

`web` 프로필은 이 제약에 맞춰 만들었다. 아트록스 vs 피오라 기준 **입력 3438 토큰 + 출력 약 500 = 약 3.9k**
로 4096 안에 들어간다. 여유가 없으므로 다음을 지킨다.

- 챔피언 이름이 길거나 지식 카드가 많은 매치업은 초과할 수 있다. 지식 카드는 서술형(콤보·라인전·스킬·힘의 구간)만 싣고,
  룬·아이템 선택은 권장안 초안 한 줄로 대체한다.
- 출력 상한을 600 토큰으로 두고 초과 시 잘리지 않게 `num_predict` 에 해당하는 값을 설정한다.
- 여유가 필요하면 B 경로로 직접 빌드해 컨텍스트를 8192 로 올리고 `compact` 프로필을 쓴다.

### 남은 준비 사항

1. **동의/고지 UI**: 다운로드 크기(A 경로 기준 약 2.5 GB), 로컬 저장(Cache API), 오프라인 추론,
   삭제 방법을 고지하고 명시적 버튼으로만 시작한다. 최초 1회 다운로드이며 이후 캐시에서 적재된다.
2. **WebGPU 게이트**: `shader-f16` 미지원 브라우저에서는 기능 자체를 감춘다. 대체 경로를 약속하지 않는다.
3. **스트리밍 UI**: web-llm 은 `chat.completions.create({ stream: true })` 로 토큰을 흘려준다.
   첫 토큰까지는 prefill 대기이므로 진행 표시가 필요하다. 소제목 단위로 나타나므로 섹션 스켈레톤을 먼저 그린다.
4. **데이터 전달**: 카드 파일 1 MB 전체 대신 챔피언별 분할(`llm/cards/<id>.json`)로 두 개만 fetch.
   `retrieval.ts` / `prompt.ts` / `playbook.ts` 는 순수 함수이므로 브라우저에서 그대로 쓴다.
5. **캐시**: 동일 (me, enemy, lane, patch) 답변은 저장한다. 결과에 "로컬 모델 생성, 지식 카드 n건 반영" 표기.
6. **지식 기여 경로**: `knowledge/` PR 기반. `npm run llm:validate` 를 CI 에 넣어 데이터 불일치를 막는다.

## 10. 실행 방법

```bash
ollama pull gemma4:e2b                       # 최초 1회
npm run llm:build                            # 사실 카드 생성
npm run llm:validate                         # 지식 계층 검증
npm run llm:matchup -- --me 아트록스 --enemy 피오라 --lane top
npm run llm:matchup -- --me 아트록스 --enemy 피오라 --dry-run      # 프롬프트 확인
npm run llm:matchup -- --me 아트록스 --enemy 피오라 --no-curated   # 지식 계층 제외(ablation)
npm run llm:matchup -- --me 아트록스 --enemy 피오라 --compact      # 툴팁 상세 제거 (약 6.2k 토큰)
npm run llm:matchup -- --me 아트록스 --enemy 피오라 --web          # web-llm 4k 예산 단일 호출
npm run llm:matchup -- --me 아트록스 --enemy 피오라 --split        # 확정 구간은 코드, 서술만 2회 호출
npm run llm:matchup -- --me 아트록스 --enemy 피오라 --chain        # 한 대화 2턴 (KV 캐시 재사용)
npm run llm:eval -- --models gemma4:e2b,gemma4:12b --variants curated,compact,web,split
```

CLI 는 항상 스트리밍으로 출력한다. 실행 후 마지막 줄에 프롬프트 토큰, **첫 토큰까지 걸린 시간**,
생성 속도, 총 시간이 찍힌다.

```
--- 프롬프트 3438 tok (4.8s) | 첫 토큰까지 4.8s | 생성 446 tok (6.9s, 64.2 tok/s) | 총 11.7s
```
