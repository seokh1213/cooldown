# PWA 릴리스와 갱신 규칙

- 게임 패치(`26.18`)와 별도로 소스·정적 에셋의 `appVersion`, 데이터 파일 내용의 `dataVersion`, 두 버전을 묶은 `releaseId`를 빌드 시 생성합니다. 같은 패치의 설명 수정도 새 버전입니다.
- 브라우저는 진입·탭 복귀·온라인 복귀와 활성 탭의 60초 주기마다 캐시를 우회해 `release.json`을 확인합니다. 게임 매니페스트는 현재 앱의 데이터 버전에 고정하고, 새 릴리스로 전환할 때 함께 교체합니다.
- 데이터는 `data/releases/<dataVersion>/...`의 변경 불가능한 주소로 제공하며, 앱의 세션 캐시도 릴리스별로 분리합니다. `public/data`의 원본 경로는 기존 링크 호환용으로 유지합니다.
- 자동 갱신은 새로고침·앱 실행 시 본문을 표시하기 전에 처리합니다. 기존 설치가 있는 온라인 진입에서 최대 3초 동안 로딩 화면을 유지하며 버전을 확인하고, 새 서비스 워커와 필요한 데이터가 준비되면 같은 URL로 갱신합니다. 첫 방문·오프라인·자동 갱신을 끈 경우에는 이 확인을 기다리지 않습니다.
- 이용 중 발견한 새 버전은 미리 설치한 뒤 다음 진입에 적용합니다. 탭 복귀·온라인 복귀·주기 확인만으로는 화면을 새로고침하지 않습니다. 진입 확인 시간이 끝난 뒤 준비된 버전도 다음 진입까지 대기합니다.
- 자동 갱신이 꺼져 있으면 안내에서 승인할 때까지 기존 버전을 유지합니다. 열린 다른 탭도 전환된 워커에 맞춰 현재 URL로 갱신합니다.
- 저장된 테마(설정이 없으면 시스템 테마)와 배경색은 앱 스크립트·스타일시트가 내려오기 전부터 적용합니다.
- 오프라인·설치 실패·데이터 준비 실패 시 현재 버전과 기존 캐시를 유지하고 다음 확인에서 재시도합니다. 사용자 선택·설정이나 다른 앱의 저장소를 초기화하지 않습니다.
- 이전 세대 PWA도 기존 `sw.js` 주소에서 새 워커로 업데이트합니다. 등록 해제용 워커나 `Clear site data`는 사용하지 않습니다.

빌드 산출물 전체를 함께 배포해야 합니다. `release.json`/`sw.js`만 별도로 교체하지 마세요. 원시 개발 서버(`npm run dev`)는 HMR을 쓰며 PWA를 새로 등록하지 않습니다. 브라우저 회귀 검사는 사용자 미리보기와 충돌하지 않도록 기본 4180 포트를 사용합니다.

갱신 화면의 검증 기준은 아래와 같습니다. 서비스 워커를 포함한 실제 빌드 A/B/C를 교체하는 `e2e/pwa-updates.spec.ts`에서 확인합니다.

| 요구사항 | 확인 방법 |
| --- | --- |
| 진입 시 이전 본문을 잠깐 표시하지 않음 | 새 버전 진입·준비된 버전 재진입에서 DOM에 나타난 챔피언 설명을 기록해 새 설명만 등장하는지 확인 |
| 이용 중 확인은 다운로드만 수행 | 탭 복귀·온라인 복귀·60초 확인 후 새 워커 준비와 기존 문서 유지 확인 |
| 느린 확인·데이터 준비는 현재 화면 유지 | 서버 응답을 보류하고 3초 뒤 기존 화면 표시, 응답 재개 후에도 버전 유지 확인 |
| 강제 새로고침 경로에서 중복 갱신하지 않음 | 서비스 워커·HTTP 캐시를 우회한 탐색이 새 버전 문서를 한 번만 여는지 확인 |
| 오프라인·실패·설정을 보존 | 오프라인 재진입, 설치·데이터 실패 후 재시도, 수동 승인·복수 탭, 사용자 설정과 다른 앱 캐시 확인 |
| 첫 배경과 테마가 일치 | 앱 JS·CSS 응답을 보류해 저장된 밝은/어두운 테마와 시스템 테마를 앱 실행 전후 비교 |

3초 제한과 로딩 해제·갱신 직전 로딩 유지의 경계는 `tests/unit/pwa-startup-gate.test.ts`에서 가상 타이머로 확인합니다. 브라우저 검사도 시간을 직접 진행해 CI 부하와 진입 제한 시간을 분리합니다.
