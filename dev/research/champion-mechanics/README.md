# 챔피언 메커니즘 JSON v2

## 목표와 책임

173명 × (공통 정보 + P/Q/W/E/R) = 1,038개 레코드다. 공통 정보 173개는 코드가 복사하고, 스킬 865개는 **gpt-6-luna / medium**이 고정 스키마 안의 내용만 작성한다. 한 챔피언의 여러 스킬을 같은 작업자에게 묶으므로 1,038번의 모델 호출이 필요하다는 뜻은 아니다.

| 코드가 관리 | Luna가 작성 | 감독자가 검수 |
|---|---|---|
| ID, 슬롯, 패치, 출처, 해시, 기존 수치·피해식, 형태 목록 | 한국어 요약, 발동 조건, 효과, 원문 근거, 모르는 부분 | 조건 누락, 대상·시점·형태 혼합, 출처 충돌, 숫자의 의미 |

현재 단계는 오프라인 데이터 작성이다. 앱의 답변 경로에 자동으로 투입하지 않는다. 전체 파일 생성과 모든 사실의 검수는 별개로 기록한다.

## 고정 구조

공통 정보는 이름·역할·스탯·공격 사거리·스킬 참조를 담는다. 스킬 작성자는 다음 세 키만 제출한다.

```json
{
  "summary": "근거에 따른 한국어 요약",
  "rules": [],
  "gaps": []
}
```

`rules`의 필드는 `variant`, `trigger`, `conditions`, `effects`, `evidence`다.

| 항목 | 의미 |
|---|---|
| variant | 공통, 변신 형태, 흐웨이 하위 스킬, 아펠리오스 무기 |
| trigger | 발동 사건과 행위자: 공격, 후속타 취소, 스탯 획득, 적중 등 |
| conditions | 대상 종류·횟수·은신·기본/추가 스탯·사용 가능 여부 등 |
| effects | 피해, 회복, 보호막, 스탯 변화/전환, CC, 이동 등 고정 종류 |
| parameters | 원문의 숫자 ID, 수치의 역할, 스탯, 랭크/레벨 범위 구분 |
| evidence | 실제 sourceId와 원문 그대로의 부분 인용 |
| gaps | 출처 부족·충돌, 숫자/조건/식 해석 불가, 형태 누락 |

효과 필드는 항상 같은 키를 가진다. 해당하지 않는 스칼라는 `null`, 목록은 `[]`다. `false`나 `0`을 모른다는 뜻으로 사용하지 않는다. 새 enum/필드를 추가하려면 작성 가이드·스키마·검증기와 버전을 함께 바꾼다.

`statSubject`는 수치가 참조하는 스탯의 주인이다. 리신 R에 충돌한 적의 피해는 날아간 주 대상의 추가 체력을 참조하므로 `stat=bonusHealth, statSubject=target`이다. 주변 인원수(`entity_count`), 적중 횟수(`hit_count`), 첫 적중 대상(`hit_order`)도 구분한다.

### 형태와 복잡한 식

제이스의 망치/캐논, 니달리의 인간/쿠거는 기존 데이터의 `form:A/B`를 복사한다. 흐웨이는 EQ/EW/EE처럼 별도 variant를 갖는다. 이 때문에 최상위 레코드는 1,038개여도 내부 규칙은 더 많다.

기존 수치·선형 피해식·계산 트리는 코드가 보존한다. 새 수치는 모델이 직접 쓰지 않고 출처의 번호를 참조한다. 퍼센트와 랭크 배열의 단위는 코드가 처리한다. 복잡한 관계를 고정 조건으로 표현하지 못하면 원문과 `gaps`를 보존한다. 텍스트 조건은 자동 실행 가능한 판정식으로 취급하지 않는다.

아펠리오스 E는 다음 무기 표시 슬롯이다. E 본문에 합쳐 들어간 무기 설명을 E의 실제 발동 효과로 만드는 것을 검증기가 거절한다.

## 출처와 검증

- 현재 패치의 영문·한국어 스킬 카드, 챔피언 상세 자료를 출처로 쓴다. 오래된 운용 노트는 이번 사실 추출의 근거에 섞지 않는다.
- 스키마가 모르는 키/enum을 거절한다. 원문 인용·숫자 ID·인용 위치·variant 출처·전환 비율을 검사한다.
- 구조 검증 통과는 `validated`다. 감독자의 사실 검수 기록이 있어야 `reviewed`로 승격할 수 있다.
- 출처·스키마·가이드 해시가 달라지면 기존 후보를 덮어써 최신으로 표시하지 않는다. 새 디렉터리에서 변경된 슬롯만 다시 작성한다.
- 툴팁에 없는 숨은 상호작용은 추측하지 않는다. 별도 조사와 근거 추가가 필요하다. 빈 `rules`는 효과 없음이라는 뜻이 아니다.

## 병렬 작업과 재개

먼저 4명으로 8개 고위험 스킬을 작성해 검수하고 계약을 확정했다. 이후 6명이 추가 챔피언을 작성했다. 한 작업자에게 140개를 한 턴에 맡기는 방식은 문맥 부담이 커서, 전체 작업은 **한 챔피언씩 새 Codex CLI 호출 / 동시 12개**로 바꿨다. 실패 복구는 4개, 독립 의미 검사는 8개에서 16개까지 병렬 실행했다. 파일 소유권을 넘겨받은 뒤 기존 후보를 건너뛰며, 실패·누락 슬롯만 재개한다.

검수는 파일 존재 → 스키마/근거 검사 → 사실 검사 순서다. 전체 후보를 만들었더라도 고위험 조건과 샘플 검수가 끝나기 전에는 앱 적용 대상으로 승인하지 않는다.

```sh
node --import tsx dev/scripts/advisor/champion-mechanics/prepare.ts
node --import tsx dev/scripts/advisor/champion-mechanics/assign.ts dev/research/champion-mechanics/26.19-v2 6
node --import tsx dev/scripts/advisor/champion-mechanics/author.ts dev/research/champion-mechanics/26.19-v2 12
node --import tsx dev/scripts/advisor/champion-mechanics/check.ts dev/research/champion-mechanics/26.19-v2 Pyke.P Akshan.P
node --import tsx dev/scripts/advisor/champion-mechanics/export.ts dev/research/champion-mechanics/26.19-v2
node --import tsx --test dev/tests/unit/champion-mechanics.test.ts
```

`prepare`는 입력/스키마/가이드/공통 정보를 만든다. `assign`은 분할 목록만 만들며 모델을 호출하지 않는다. `check`는 후보를 검사하며 승인하지 않는다. 실제 작성 모델/effort는 실행 도구에 명시적으로 지정한다. 세션 식별자는 저장소에 넣지 않는다.

`author`는 고정 스키마와 전체 키트 출처를 `codex exec -m gpt-6-luna` / `model_reasoning_effort=medium`에 전달한다. 다른 모델로 자동 전환하지 않는다. 잘못된 JSON은 오류 목록을 붙여 최대 한 번 추가 작성한다. API가 지원하지 않는 `uniqueItems`만 생성 제약에서 빼며, 로컬 검증기는 계속 중복을 거절한다. `export`는 865개 후보가 전부 유효하고 현재 출처 해시가 같을 때만 레코드를 조립한다. 검수 결정은 출처·후보 해시가 일치해야 유지된다.

`recover`는 호출이 끝난 실패 묶음에서 유효한 슬롯을 먼저 복구하고 나머지만 재작성한다. `screen`은 별도의 Luna 호출로 원문과 후보의 의미를 대조한다. 그 지적도 오탐이 있어 감독자가 재확인하며, 자동 검사만으로 `reviewed`로 올리지 않는다. `repair-screen`은 후보 해시가 같은 지적만 작성자에게 돌려보낸다.

숫자 인용을 보완하는 코드는 해당 숫자가 있던 원문 문장만 복사한다. 숫자가 실제로 횟수·거리·피해 계수 중 무엇인지까지 증명하지는 않는다. 현재 체력·잃은 체력 등 계약에 없는 표현은 원문 텍스트와 `gaps`로 보존한다. 이 데이터의 규칙을 완전한 게임 계산식으로 실행해서는 안 된다.

## 생성 결과와 검수 범위

공통 정보 173개와 스킬 후보 865개를 모두 작성했다. 결과물은 `overview/`와 `records/`, 원문 입력은 `inputs/`, 모델 초안은 `candidates/`에 있다. 최종 집계와 검수 범위는 [최종 검수 보고서](26.19-v2/reports/final-review.md)를 확인한다. 실제 게임의 숨은 상호작용과 앱 답변 품질은 별도 검증이 필요하다.

스킬 865개 전부 감독 검수와 승인을 마쳤으며 승인 대기는 0개다. 잔여 774개 중 746개를 수정했고, 과거 미확정 지적 736건도 모두 판정했다. 상세 수정·근거·해시 기록은 [전수 검수 보고서](26.19-v2/reports/final-review.md)에 있다.

[CI 변경 감지와 갱신 절차](MAINTENANCE.md)도 구현했다. 전체 승인 자료로 [답변 비교](../llm-evals/champion-mechanics-v2/README.md)를 다시 실행한 결과, 기존 고정 51턴은 현행 26턴 → 실험 50턴, 새 18턴은 2턴 → 7턴이었다. 두 질문셋 모두 현행 대비 퇴보는 없었다. 새 스킬 전반의 답변을 개선하려면 질문 해석과 검색 범위를 더 보완해야 한다. 앱 연결은 별도 단계다.

이번 실행에서 Orca의 터미널 준비 인식은 두 차례 실패했고 작업을 전달하지 못했다. 잔여 터미널을 해제하고, 제공된 collaboration 에이전트 도구로 `gpt-6-luna`, `medium`을 명시해 병렬 작성한다. Orca에서 작성됐다고 주장하지 않는다.
