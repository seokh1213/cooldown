# 두 판정의 불일치를 0.8B로 재판정

이번 설정은 기존 혼합 방식보다 나빴다. 운영에 적용하지 않았다. 높은 확신의 오류를 검토할 수 있었지만, 맞던 답을 보존하지 못했다.

## 시험한 구조

1. 현재 문자 로지스틱의 1위 범위와 0.8B의 전체 11범위 판정을 각각 구한다. 기존 0.6·0.2 기준을 넘어선 질문도 비교한다.
2. 두 범위가 같으면 채택한다. 다르면 같은 0.8B에 두 후보의 설명만 주고 재판정한다. 후보는 정렬하며 점수와 어느 판정기가 골랐는지를 보내지 않는다.
3. 재판정은 `scope`, `slots`, `breadth`, `excludedScopes`, `evidence`를 JSON으로 반환한다. 후보 둘 또는 `clarify`만 선택할 수 있다.
4. 형식 실패, 실제 질문에 없는 인용, 선택한 범위를 동시에 제외한 응답은 되묻기로 처리한다. 되묻기는 정답으로 세지 않는다.

최초 0.8B 프롬프트는 이전 단독·혼합 시험과 동일하다. 언어별 예시 15개와 전체 11범위 선택, temperature 0, seed 42, thinking off를 유지했다. 재판정 예시는 기존 학습 자료의 첫 문장들을 구조화했고, 시험 정답을 예시나 모델 입력에 넣지 않았다. 두 후보에 해당하는 예시만 전달한다. 질문 낱말을 검사해 범위를 고치는 규칙은 추가하지 않았다.

재판정 예시는 범위별 11개와 정정 예시 4개, 언어마다 15개다. 스킬 슬롯·전체 여부·제외 범위·인용을 검수해 고정한 `request-review-examples.json`을 사용한다. 처음 프롬프트와 재판정 프롬프트 모두 같은 Ollama Qwen3.5 0.8B Q8_0 및 digest를 쓴다. `keep_alive: 5m`으로 재사용하며, 프롬프트별 대화 입력은 별도로 만든다. 동일 요청은 이전 캐시를 재사용한다. 캐시를 포함한 재실행 시간은 모델 추론 속도로 보고하지 않는다.

## 결과

한국어·영어·중국어 일반 질문 99개, 부정·정정 36개, 기존 앱 대화 9개·33턴으로 비교했다.

| 방식 | 일반 / 99 | 부정·정정 / 36 | 대화 처리 / 33 |
| --- | ---: | ---: | ---: |
| 현행 | 75 | 20 | 27 |
| 낮은 확신만 0.8B로 보완 | 82 | 28 | 28 |
| 처음부터 0.8B 단독 | 68 | 28 | 15 |
| 두 판정 비교 후 불일치 재판정 | 74 | 29 | 14 |

재판정 호출은 일반 47/99개, 정정 19/36개였다. 일반 9개, 정정 4개를 되물었다. 기존 혼합 방식과 비교하면 일반에서 오답 6개를 고쳤지만 맞던 14개를 잃었다. 정정에서는 오답 3개를 고치고 맞던 2개를 잃었다. 되묻기도 잃은 답에 포함한다.

실제 대화에서는 최초 0.8B 판정 33회와 재판정 24회, 합계 57회의 논리적 모델 판정이 필요했다. 기존 혼합 방식은 6회였다. 실제 대화의 11턴을 되물었다. 최초 두 요청은 Node의 `Promise.all`로 함께 시작한다. 이 시험은 같은 Ollama 요청을 캐시에서 재사용하므로 병렬 실행의 체감 속도를 검증한 것은 아니다. 앱에서 같은 0.8B의 여러 작업은 기존 워커 큐로 순서대로 처리한다.

대화는 네 정책을 같은 실행에서 `answerDialogue`, 계획기·답변 조립·저장 복원에 주입해 비교했다. 기각되면 실험 래퍼가 추측한 답을 버리고 되묻기 문장으로 바꾸며 이전 대화 기억을 보존한다. 이 래퍼는 운영 기능이 아니다. 원래 현행·혼합·단독의 27·28·15턴 결과가 같은 실행에서도 유지됐다.

## 발견한 실패

높은 확신으로 틀린 영어의 “기본 정보와 스킬을 함께”는 소개 범위로 고쳤다. 한국어의 “스탯은 알았으니 전체 스킬”에서는 스킬을 골랐지만, 근거로 다른 학습 예시 문장을 복사해서 기각됐다. 중국어의 한타 위치 질문은 재판정도 상대법으로 골랐다. 정정 질문의 도우미 사용법은 두 후보가 `other`와 `chat`이라 정답 `identity`를 고를 수 없었다.

스킬 정보에서도 구조화가 자동으로 올바른 범위를 만들지는 않았다. “R 스킬정보”에서 `slots: ["R"]`, `breadth: "specific"`을 추출하고도 `scope: "skills"`를 골랐다. 공속 하나나 체력·체젠 두 항목도 전체 스탯으로 보내는 오답이 남았다. 형식 검사와 인용 존재 검사는 이런 의미 오류를 검출하지 못한다.

기각된 대화 11턴 중에는 학습 예시 복사 외에도 인용의 대소문자·공백 차이가 있다. 엄격한 인용 검사는 올바른 범위를 고른 응답까지 기각할 수 있다. 따라서 14/33은 작은 모델 자체의 일반적 능력 점수가 아니라, 이번 프롬프트와 검증 조건을 포함한 정책 결과다.

## 결정과 한계

이 재판정 정책을 운영에 연결하지 않는다. 불일치가 높은 점수의 오류를 발견하는 신호는 되지만, 같은 모델에 한 번 더 묻는 것만으로 안전하게 수정할 수 있다는 근거는 얻지 못했다. 다음 개선 후보는 범위 판정의 학습 자료 보강 또는 검증된 임베딩 판정기이며, 이번에는 추가 학습이나 다른 프롬프트 탐색을 하지 않았다.

이는 앞선 질문과 실패를 본 뒤 설계한 소규모 회귀 시험이다. 독립적인 실사용 정확도, 답변의 게임 지식 정확도, 모바일·브라우저 Q4·kev LoRA 성능을 증명하지 않는다. 후보 둘에 정답이 없으면 재판정이 정확한 범위를 선택할 수 없고, 두 판정이 같은 오답을 내면 재검토하지 않는다.

## 재현과 검증

프로젝트 루트에서 같은 로컬 Ollama를 사용해 순서대로 실행한다.

```sh
uv run --python 3.13 --with numpy==2.5.3 --with scikit-learn==1.9.1 python dev/scripts/advisor/offline-classifier/test_request_review.py
uv run --python 3.13 --with numpy==2.5.3 --with scikit-learn==1.9.1 python dev/scripts/advisor/offline-classifier/evaluate-request-review.py
npx tsx dev/scripts/advisor/offline-classifier/evaluate-request-hybrid-flow.ts --dual-review
```

6개 독립 테스트는 모델 호출 없이 입력 격리, 합의 시 재판정 생략, 존재하지 않는 인용·제외된 범위·불완전한 출력의 기각을 검증한다. ESLint와 스크립트 타입 검사도 통과했다. 범위 결과·원문 출력은 `dual-review.json`, 실제 대화와 기억 복원 결과는 `flows-dual-review.json`에 기록했다. 소스 해시는 각 보고서에 남겼다.
