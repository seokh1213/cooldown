# 부정·정정 요청의 학습과 LLM 판정

## 질문과 시험

앞선 임베딩 분류기가 “스탯은 이미 알았으니 스킬을 설명해줘”를 스탯 요청으로 보냈다. 부정문 학습이 가능한지, 임베딩 자체의 한계인지, 로컬 0.8B LLM을 사용하면 나아지는지 확인했다.

운영 모델은 변경하지 않았다. 원래 학습 문장 665개에 부정·정정 예시 48개를 추가한 연구 모델을 학습했다. 추가 예시는 한국어·영어·중국어 각각 16개다. 스킬과 스탯으로 서로 반대 방향의 전환을 묻는 예시를 같은 수로 넣고, 전체 소개와 도우미 사용 안내도 포함했다. 코드에 새 단어 규칙을 추가하지 않았다.

별도의 새 시험 문장은 언어별 12개, 총 36개다. 같은 문장에서 주제의 순서를 바꾼 스킬·스탯 전환 12쌍도 포함한다. 원래 학습 문장 및 보강 문장과 정규화 후 정확한 중복이 없음을 검사했다. 기존 시험 66개와 추가 질문 99개도 함께 평가해 다른 범위의 손실을 확인했다. 기존 99개는 오류를 보고 보강 방향을 정했으므로 이제 회귀 자료로 취급한다.

임베딩 인코더는 고정하고 로지스틱 분류기만 재학습했다. C는 앞선 실험의 값을 그대로 사용하고 새 시험으로 선택하지 않았다. 문자 모델은 운영과 같은 이름 개수 균형 학습을 사용했으며, 보강 모델의 가중치를 fp16으로 내보내지는 않았다.

## 예시 보강 결과

| 판정기 | 새 부정·정정 36개, 전 → 후 | 기존 시험 66개, 전 → 후 | 기존 추가 질문 99개, 전 → 후 |
| --- | ---: | ---: | ---: |
| Arctic + 로지스틱 | 20 → 28 | 65 → 65 | 96 → 97 |
| E5-small + 로지스틱 | 19 → 25 | 63 → 63 | 91 → 92 |
| 문자 + 로지스틱 | 20 → 33 | 64 → 62 | 75 → 78 |

보강으로 개선되므로 부정·정정 요청을 분류기가 학습할 수 있다는 증거는 있다. 동시에 예시 48개만 보강해서 모두 해결됐다는 결과는 아니다. 문자 모델은 이 작은 시험에서 좋았지만 기존 66개에서 정답이 2개 줄었다.

반대 방향 질문 쌍의 두 문장을 모두 맞힌 수는 Arctic 2 → 5 / 12, E5 0 → 2 / 12, 문자 2 → 9 / 12였다. 임베딩 분류기는 특히 스킬·스탯 두 주제를 함께 언급하는 질문에서 최종 요청의 방향을 여전히 놓쳤다.

### 채택과 오답

위 표는 기각 전 1위 범위다. 같은 운영 기준(최댓값 0.6, 1·2위 차이 0.2)을 적용한 새 36개 문장의 채택 수와 그중 오답은 아래와 같다.

| 보강 판정기 | 채택 / 36 | 채택 중 오답 |
| --- | ---: | ---: |
| Arctic | 19 | 1 |
| E5-small | 15 | 2 |
| 문자 | 14 | 1 |

문자 모델의 33/36을 바로 운영 답변 성공률로 해석할 수 없다. 기각한 판단을 기존 단어 규칙으로 돌리면 다시 오류가 날 수 있다. 보강한 Arctic도 중국어의 “속성은 알고 있으니 스킬 설명”을 스탯 요청으로 높은 점수로 분류했다. 확신이 낮은 질문만 확인하는 경로로 모든 오답을 잡을 수 있는 것도 아니다.

## 로컬 0.8B LLM

Ollama `qwen3.5:0.8b` Q8_0, 고정 digest를 사용했다. 생각 출력은 끄고 temperature=0, seed=42, 최대 생성 40토큰으로 범위 11개 중 하나를 JSON으로 받았다. 질문마다 독립 대화이며, 답변 생성이나 앱 대화 이력 처리를 시험한 것이 아니다. 앱의 kev LoRA 판정 그래프와도 다른 실행이다.

첫 설정은 범위의 설명만 주는 zero-shot이었다. 두 번째는 같은 설명에 새 학습 자료의 각 언어·범위 첫 문장을 넣었다. 4범위 × 3언어, 총 12개의 질문·정답 예시이며 시험 문장은 넣지 않았다. few-shot은 모델 가중치를 학습한 것이 아니라 프롬프트에서 예시를 제공한 것이다.

| 설정 | 새 부정·정정 / 36 | 앞선 Arctic 오분류 / 3 |
| --- | ---: | ---: |
| 범위 설명만 | 9 | 0 |
| 학습 예시 12개 제공 | 33 | 3 |

예시를 준 설정은 반대 방향 질문 쌍 11/12를 모두 맞혔다. 남은 오답은 한국어의 “체력표는 확인했어, 이번에는 P Q W E R”을 전체 소개로, 한국어·영어의 “공략은 됐고 여기서 어떤 질문을 지원하나”를 각각 잡담·스킬로 분류한 것이다. 한 문장 판정의 로컬 응답 시간 중앙값은 약 268ms였다. 첫 요청은 제외했으며 모바일 WebGPU 속도를 뜻하지 않는다.

좋아 보인 few-shot 프롬프트를 고정한 뒤 기존 11범위 질문 99개에 적용했다. 결과는 **55/99**였다(한국어 20/33, 영어 18/33, 중국어 17/33). 예시는 소개·스탯 전체·스킬 전체·도우미 안내 네 범위만 포함하므로 전체 범위가 균형 잡힌 LLM 학습 비교는 아니다. 이 설정을 전체 요청 판정기로 추천할 수 없다는 검증 결과이며, 모든 LLM 또는 모든 프롬프트가 부정문에 약하다는 증거는 아니다.

## 해석과 다음 기준

원래 학습 자료에도 “말고”, “Not stats”, “不要” 예시는 있었다. 빠진 것은 부정 단어 자체만이 아니라, 이미 설명한 주제를 언급하면서 다른 주제로 전환하는 표현의 다양성이다. 문장 전체의 고정 벡터 위에 선형 분류기를 학습하는 현재 구조에서 그 관계를 구별하는 결정 경계가 충분히 학습되지 않았다는 해석이 이번 결과와 맞는다. 임베딩에서 부정 정보가 완전히 사라진다고 단정하지 않는다.

임베딩 인코더 자체를 학습하는 방법도 있다. 예를 들어 [SimCSE](https://arxiv.org/abs/2104.08821)는 자연어 추론 자료의 함의·모순 문장 쌍을 학습 신호로 사용한다. 이번에는 인코더 미세 조정, LoRA, 토큰 단위 요청 추출을 시험하지 않았다.

다음 판정기는 일반 요청과 정정 요청을 함께 포함한 자료로 학습하고, 언어별 새 표현·반대 방향 쌍·기존 질문·실제 대화 조건을 모두 통과해야 한다. LLM은 JSON 의도 판정의 후보이지만, 현재 0.8B의 특화 프롬프트를 전체 경로에 적용하면 성능을 잃는다. 낮은 확신을 기존 낱말 규칙으로 보내는 경로도 함께 정리해야 한다.

## 재현과 한계

프로젝트 루트에서 실행한다. 앞선 [10조합 비교](../README.md)의 두 임베딩 캐시가 필요하며, 원래 캐시와 운영 가중치는 덮어쓰지 않는다.

```sh
npx tsx dev/scripts/advisor/offline-classifier/embed-request-negation.ts
uv run --python 3.13 --with numpy==2.5.3 --with scikit-learn==1.9.1 python dev/scripts/advisor/offline-classifier/compare-request-negation.py
uv run --python 3.13 --with numpy==2.5.3 --with scikit-learn==1.9.1 python dev/scripts/advisor/offline-classifier/evaluate-request-negation-llm.py
uv run --python 3.13 --with numpy==2.5.3 --with scikit-learn==1.9.1 python dev/scripts/advisor/offline-classifier/evaluate-request-negation-llm.py --few-shot
uv run --python 3.13 --with numpy==2.5.3 --with scikit-learn==1.9.1 python dev/scripts/advisor/offline-classifier/evaluate-request-negation-general-llm.py
```

LLM 호출은 로컬 서버의 같은 모델을 쓰므로 순서대로 실행한다. JSON에는 실제 출력, 오답, 설정, 소스 해시를 기록한다. 새 36개도 같은 작성자가 만든 작은 수작업 모음이며 실사용 전체 정확도 추정이 아니다. 연구 단계의 범위 판정 시험만 완료했고 실제 대화·브라우저 연동이나 운영 적용은 하지 않았다.
