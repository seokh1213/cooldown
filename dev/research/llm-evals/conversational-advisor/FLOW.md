# 대화 흐름 정리

2026-10-01. 채택된 답변 동작을 유지하면서 요청의 생애주기를 드러낸다.

후속 정리에서 새 상성의 이름 수별 처리기 세 개를 합쳐 기본 처리기는 9개가 됐다.
현재 목록과 실제 모델 회귀 비교는 [9개 처리기 점검](NINE_STAGE_CHECK.md)에 있다.
아래 11개 목록과 검증 수치는 최초 구조 정리 당시의 기록이다.

## 완료 기준

- [x] 앱의 진입점에서 맥락 복원·질문 계획·근거 조립·기록의 경계를 읽을 수 있다.
- [x] 혼합 질문·대상 확인·수치 정정·주제 복귀는 기존 동작을 유지한다.
- [x] 기존 11개 처리기의 우선순위를 유지하고, 이해·조회·상성·개별 대상의 책임을 분리한다.
- [x] 전후 질문 재생, 집중 테스트, 전체 테스트·타입·린트·빌드로 회귀를 확인한다.
- [x] 실제 Chrome에서 입력·정정·기록 복원을 확인하고 구조 변경을 별도 커밋한다.

## 네 단계

| 단계 | 담당 코드 | 입력 → 출력 |
|---|---|---|
| 맥락 복원·요청 준비 | `dialogueRequest.prepareDialogueRequest` | 질문·대화 기록 → 이번 요청과 기억 |
| 질문 해석·계획 | `dialoguePlanner.planPreparedDialogue` | 요청·기억 → 하위 질문별 자료 계획 또는 확인 질문·다음 기억 |
| 근거 답변 조립 | `dialogueReply.assembleDialogueReply` | 계획·자료 → 카드/본문과 해당 시점의 기억 |
| 대화 기록 | `useAskAdvisor.recordReply` → `useAdvisorTurns`·`history` | 답변·기억 → 같은 대화 턴의 표시·저장 |

앱은 `dialogueFlow.answerDialogue`로 처음 세 단계를 실행하고 결과를 기록한다.
자료가 아직 준비되지 않은 경우도 같은 진입점을 사용하며 기존 생성/동의 안내 계획을 돌려준다.
화면 훅에 있던 별도의 답변 계획 실행 분기는 제거했다.

기억은 `DialogueMemory`, 대화 턴은 `DialogueHistoryTurn`, 모델/검색 경계는 `PlanDeps`가 표현한다.
기억 갱신은 `rememberDialoguePlan`에서 수행한다. 화면, React, 저장 구현을 대화 도메인에 넣지 않는다.
기존 실험의 부분 조합은 `planDialogue`와 `DialogueVariant`로 재현할 수 있다.

## 기존 11개 처리기

기존 자료 조회 처리기 11개를 다음 책임으로 묶었다.
`planAnswer`는 `understand`로 질문을 한 번 이해하고 다음 순서에서 첫 답을 선택한다.

1. **지식 조회** (`knowledgePlans`): 벡터 검색 → 룬/주문 규칙 → 이름 정정 → 게임 사실.
2. **상성** (`matchupPlans`): 이어 묻기 → 최근 챔피언과 짝짓기 → 이름 셋 이상 → 이름 둘.
3. **개별 대상** (`championPlans`): 아이템/원리 → 챔피언.
4. **노트** (`knowledgePlans`): 마지막 낱말 검색.

판정 헤드 이름과 입력/출력 계약은 각각 `judgeHeads`·`planTypes`로 분리했다.
기존 `plan`의 공개 import 경로는 유지했다. 판정 방식·계산식·질문셋·게임 자료는 바꾸지 않았다.

## 검증 기록

- 모델을 호출하지 않는 동일한 74턴 재생에서 전후의 계획·기억 상태가 모두 일치했다.
  이번 검사는 구조 변경의 회귀 비교이며, 이전 0.8B 브라우저 평가를 새로 측정한 점수가 아니다.
- 앱 진입점 집중 테스트 5개를 추가했다: 혼합 질문 본문, 저장·복원 후 정정, 확인 답의 관점,
  확인 질문 이전의 답 보존, 자료 준비 전 응답 계획. 기존 대화·계획 테스트와 함께 144개 통과.
- 전체 `npm test` 1,394개 통과. `npm run type-check`, `npm run lint`, `npm run build`, `git diff --check` 통과.
  빌드의 기존 600 kB 청크 경고는 유지된다.
- 이동한 함수 본문을 원본과 대조했다. 원본의 `planAnswer`는 처리기 목록을 책임별로 묶었고,
  `continueMatchup`은 주제 함수의 인자를 객체로 전달한다. 다른 원본 함수의 본문은 같다.
  이번에 수정·추가한 파일과 함수는 400줄/100줄 및 인자 4개 제한을 넘지 않는다.
- 격리된 headless Chrome DevTools에서 **모델 없이 써보기**로 실제 입력창을 확인했다.
  럭스 궁 2랭크·가속 75 → 28.57초, 가속 100 정정 → 25초,
  새로고침 후 새 질문 “같은 조건에서 럭스 궁은 몇 초야?” → 2랭크·가속 100·25초를 확인했다.
  콘솔 오류 0건. [실제 화면의 대화 기록](flow-ui.txt).
