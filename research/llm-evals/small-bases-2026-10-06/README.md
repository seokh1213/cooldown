# 소형 베이스 세 종의 의미 질문 SFT, 2026-10-06

첫 파일럿의 우선 후보는 **Qwen3.5 0.8B + 새 QA LoRA**다. 실제 WebGPU에서 정답 있는
새 질문은 82/136에서 107/136으로, 동결 앱이 선택한 문서로 답한 경우는 67/132에서
92/132로 개선됐다. 모델 본체는 adapter를 포함해 616.9MB다. 기본 앱 모델·응답은
변경하지 않았다. 이 결과는 한국어 수치 QA의 개선이며 전체 챗봇 품질 점수가 아니다.

## 무엇을 바꿨나

같은 기반에서 원문 앵커 뒤 숫자를 복사하던 기존 SFT를 그대로 연장하지 않고, 새
adapter를 만들었다. 질문이 가리키는 값·조건·단위를 고르고 잘못된 문서에서는
NOT_FOUND를 답하는 데이터를 학습했다. 다른 베이스도 같은 데이터를 받았다.

- **Qwen/Qwen3.5-0.8B:** 현행과 같은 backbone. 기존 분류·검색 LoRA를 보존한 QA gate를 추가했다.
- **Qwen/Qwen2.5-0.5B-Instruct:** 이전 세대의 일반 attention 구조와 작은 파라미터 수를 비교했다.
- **LiquidAI/LFM2.5-350M:** 10개 convolution·6개 attention 층의 다른 구조와 더 작은 본체를 비교했다.

LoRA는 응답 행동을 학습하고 backbone 층 구성은 유지한다. LFM 비교는 다른 구조를
실제로 시험하는 경로다. 0부터 언어 모델을 사전학습하거나 dense FFN을 MoE로 개조하는
작업은 이번 파일럿에 포함하지 않았다. 제한된 도메인 QA와 Colab으로 먼저 확인할
대상은 기존 소형 베이스의 작업별 adapter다.

[GLM-4.7-Flash](https://huggingface.co/zai-org/GLM-4.7-Flash)는 전체 30B·활성 3B MoE다.
전체 가중치를 4bit로만 계산해도 약 15GB여서 이번 1GB 제한에 맞지 않는다. 활성
파라미터 수를 다운로드 용량으로 사용하지 않는다. Flash라는 이름만으로 소형이라고
판단하지 않았다.

## 학습·시험 조건

수작업 사실 105개에서 네 가지 질문 표현을 만들었다. 학습은 415개, dev는 110개다.
학습 332개 양성·83개 다른 문서 음성, dev 88개 양성·22개 음성이며 실제 사용자
대화 로그가 아니다. 정답·음성 문서 모두 시험 문서와 겹치지 않는다. 질문만으로
1,300자 문맥을 고르고 정답 문장·위치로 자르지 않는다.

세 모델 모두 fresh all-linear LoRA rank 16·alpha 32, AdamW 1e-4, weight decay .01,
accumulation 8, seed 20261006, 1 epoch다. FP32 frozen weights와 CUDA FP16 autocast를
사용했고 정답 토큰만 loss에 넣었다. 프롬프트 상한 1,900토큰, greedy 답변 상한
24토큰과 모델별 원래 tokenizer·chat template을 사용했다. Unsloth는 사용하지 않았다.

시험은 기존 36개와 새로운 176개, 총 212개를 고정했다. 새 양성 136개는 17개 문서의
68개 사실을 두 번씩 바꿔 묻는다. 독립 표본 136개로 해석하지 않는다. 음성 40개는
같은 문서의 없는 필드 20개와 다른 문서 20개다. 숫자·단위·부호·범위를 정확히
비교하며 양끝 공백만 제거한다. 오류의 값 선택과 단위·표기 차이를 따로 기록했다.

앱 근거 132개는 source commit `4d6267596bb9ee9f9a35877dce09377574ac1084`의 실제
분류·검색으로 이미 선택한 문서다. 당시 정답 문서 도달은 112/132이며 이후 앱
수정은 비교에 섞지 않았다. 상충하는 포탑 방패 값의 4문항을 이 경로에서 제외했다.
검색·분류 자체를 대체한 세 새 앱을 평가한 것이 아니다. 카드의 정답 문자열 포함
110/132도 아래의 정확한 수치 생성 점수와 다르다.
정답은 동결 문서 기준이다. 현재 게임 규칙의 정확성과 최신성을 검증한 점수로 사용하지 않는다.

## 실제 양자화 모델의 WebGPU 결과

Mac 32GiB·Apple Metal 3·Chrome 154에서 세 모델을 각각 212+132개, 전후 688회
평가했다. runtime은 Transformers.js 4.3.0과 ORT Web 1.31.0-dev.20260914-8d85527a0다.
모바일과 다른 브라우저의 동작을 보증하지 않는다.

| 모델 | 새 양성 | 답 없는 문맥 | 앱 근거 후 정답 | 문서 숫자 검사도 통과한 오답 |
| --- | ---: | ---: | ---: | ---: |
| 현행 Qwen 0.8B | 82/136 | 16/40 | 67/132 | 23 |
| 새 QA Qwen 0.8B | **107/136** | **30/40** | **92/132** | **15** |
| 새 QA Qwen2.5 0.5B | 88/136 | 21/40 | 72/132 | 39 |
| 새 QA LFM 350M q4f32 | 90/136 | 26/40 | 76/132 | 33 |

새 질문 전체는 Qwen 98→137/176, Qwen2.5 47→109/176, LFM 45→116/176이었다.
각 대안의 앱 근거 전후는 Qwen2.5 34→72/132, LFM 7→76/132다. 기존 36개는
새 Qwen 34/36, Qwen2.5 31/36, LFM 35/36이었다. 이 작은 회귀셋만으로 후보를
선택하면 새 질문·앱 근거에서의 차이를 놓친다.

Qwen의 같은 사실 두 표현을 모두 맞힌 그룹은 33→47/68이었다. 앱에서 틀린 값을
답한 경우는 37→17개, 단위·표기는 18→7개다. 거절 10→16개에는 검색이 잘못
고른 문서를 거절한 경우도 들어가므로 전부 생성 오류라고 해석하지 않는다.

전후 정확도 비교는 같은 통합 graph에서 QA gate 0/1을 교차했다. 이 baseline에는
adapter 계산 비용이 포함되므로 그 시간을 원본 모델의 속도로 사용하지 않았다.
원본·새 graph의 tensor 보존과 기존 분류·검색 특징의 일치를 별도로 확인했다.

**숫자가 문서에 있다는 검사만으로 답을 공개하면 새 Qwen에서도 오답 15개가 남는다.**
이 검사를 의미 검증으로 취급하지 않는다. 이전 631개 anchor SFT는 Mac CPU에서
양성 85/136·앱 72/132·검사 통과 오답 11개였다. 새 결과와 runtime이 다르므로
그 후보의 WebGPU 점수로 바꿔 말하지 않는다. 기존 카드 응답을 자동 교체하지 않았다.

## 원본 가중치와 양자화의 차이

세 모델의 native 전후 평가도 각각 688회 끝냈다. 아래는 새 adapter의 점수다.

| native FP32 + FP16 autocast | 새 양성 | 답 없는 문맥 | 앱 근거 후 정답 |
| --- | ---: | ---: | ---: |
| Qwen3.5 0.8B | 113/136 | 29/40 | 97/132 |
| Qwen2.5 0.5B | 101/136 | 27/40 | 83/132 |
| LFM2.5 350M | 93/136 | 32/40 | 77/132 |

native Qwen은 앱 70→97/132, 새 양성 88→113/136이었다. 양자화·브라우저에서는
그 증가분 일부가 줄어든다. native 점수를 실제 배포 성능으로 보고하지 않는다.
T4에서 Qwen의 학습과 후속 dev loss 측정은 894.3초, LFM은 146.2초였다. Qwen2.5의
재개 후 13.4초는 완료 학습 상태의 후속 dev 측정이며 전체 학습 시간으로 세지 않는다.

Mac ORT CPU에서 LFM 두 graph의 전체 688회 비교도 완료했다. q4는 양성 87/136·
음성 29/40·앱 71/132, q4f32는 90/136·26/40·75/132였다. Qwen2.5 CPU 152회와
Qwen3.5 CPU 328회는 부분 검증으로 보존하고 전체 평가에 세지 않았다. 이후의
양자화 후보 전체 비교는 위 WebGPU 결과를 사용했다.

## 파일 크기·속도

MB는 1,000,000바이트, MiB는 1,048,576바이트다. 아래 본체 크기는 graph와 외부
가중치 합계이며 tokenizer·앱 자료와 RAM 사용량은 포함하지 않는다.

| 학습한 graph | 본체 크기 | 추가 adapter |
| --- | ---: | ---: |
| Qwen3.5 0.8B q4 | 616.9MB / 588.3MiB | 21.6MB |
| Qwen2.5 0.5B q4 | 821.5MB / 783.5MiB | 35.2MB |
| LFM 350M q4 | 317.9MB / 303.2MiB | 24.0MB |
| LFM 350M q4f32 | 505.3MB / 481.9MiB | 24.0MB |

현행 Qwen 본체는 595.0MB / 567.5MiB다. 작은 파라미터 수가 더 작은 ONNX 파일을
보증하지 않는다. 별도 작은 모델을 답변에만 추가하고 기존 Qwen 분류·검색도 유지하면
두 본체의 용량이 합산된다. 예를 들어 Qwen+LFM q4f32는 본체만 약 1.10GB다.
LFM 단독 505MB를 앱 전체 다운로드 크기로 보고하지 않는다. 완전 대체에는 해당
backbone의 분류·검색 학습과 검증도 필요하다.

12개 질문을 두 번씩, 모델별 1회 warm-up 뒤에 원본 graph와 학습 graph를 별도로
로드해 순차 측정했다. 전처리된 token을 사용하고 다운로드·검색·토큰화·최초 compilation은
제외했다. 서로 다른 출력 길이도 걸린 시간에 영향을 준다. localhost의 캐시된 파일
적재 시간을 인터넷 다운로드 시간으로 사용하지 않는다.

| Mac WebGPU 생성 | 중앙값 | p95 |
| --- | ---: | ---: |
| 현행 Qwen 원본 graph | 0.669초 | 0.945초 |
| 새 QA Qwen 0.8B | 0.767초 | 1.100초 |
| 새 QA Qwen2.5 0.5B | 0.558초 | 0.818초 |
| 새 QA LFM q4f32 | 0.318초 | 0.436초 |

이 표본에서 새 Qwen은 약 0.10초 느려졌고 두 대안은 더 빨랐다. 속도·용량의 장점과
정확한 값 선택·오답 노출의 차이를 함께 판단한다. 12개 속도 표본을 전체 질문의
성능이나 모바일 지연으로 일반화하지 않는다.

## 복구·보존·종료

약 60초 또는 40개 학습 행마다 optimizer 업데이트 경계에서 저장하고, 맥은 60초마다
확인했다. full optimizer·GradScaler·난수·진행·입력 해시를 포함한 archive를 크기와
SHA-256·tar 경로로 검증하고 각 단계의 최근 3개를 보존한다. 맥이 꺼져 있거나
네트워크가 끊기면 새 로컬 다운로드는 멈춘다.

첫 Colab VM이 실제 종료된 뒤 LFM 최종 결과와 Qwen2.5의 415행 완료 checkpoint를
맥에서 새 T4로 복원했다. Qwen2.5는 `resumedFromRow=415`이며 추가 epoch 없이
남은 평가를 마쳤다. 종료 원인은 확정하지 않았다. 두 번째 실행은 kernel foreground
셀에서 파이프라인을 실행했다. 모든 최종 archive를 맥에서 재검증한 뒤 소유 GPU만
자동 종료했고 활성 Colab assignment 0을 확인했다.

Qwen 186개, Qwen2.5 168개, LFM 92개 투영에 adapter가 대응했다. 네 export에서
원본 serialized tensor가 유지됐고 Qwen의 기존 분류·검색·일반 특징 18개는 정확히
같았다. Python 집중 테스트 63개 통과. 모델·평가·checkpoint는 로컬 cache에 보존한다.
인증 설정·원격 식별자·private log·전체 모델 가중치는 Git과 Vault에 넣지 않는다.

재현 조건과 명령은 [도구 README](../../../scripts/llm/tuning/README.md)의 세 베이스
SFT 절에 있다. [계획](plan.json)과 [기계 판독 결과](comparison.json)에 revision,
입력·출력 해시와 점수를 보존한다. 원본 모델의 기본 앱 설정을 바꾸지 않았다.
