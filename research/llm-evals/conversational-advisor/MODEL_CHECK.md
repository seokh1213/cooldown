# 최신 대화 흐름의 실제 0.8B 재검증

2026-10-01 · 자료 26.19 · 최종 실행 코드 `1c6b7539a`

앞선 [master 점검](MASTER_CHECK.md)은 모델 없이 앱 흐름을 확인했다.
이번에는 앱의 Qwen3.5 0.8B q4 워커를 실제 WebGPU에서 실행하고,
사전 등록된 74턴과 모델을 켠 입력창 대화를 함께 확인했다.
검증 도중 원문과 화면에서 발견한 세 회귀를 고친 뒤 74턴을 다시 수집했다.
최신 master의 스킬 폼·레벨 수치 수정 `2644e8ac1`까지 포함한 상태다.

## 이전보다 좋아졌는가

최초 구조보다 질문의 대상과 이어 묻기가 개선됐고, 최신 변경에서도 최초 결합 후보의 성능을 유지했다.
자유 대화 전반의 자연성이나 모든 게임 지식의 정확성을 새로 검증한 결과는 아니다.

|---|---:|---:|---:|
| 경로·대상·주제·슬롯 | 50/74 | 74/74 | 74/74 |

원래 `current.json`과 `combined.json`은 과거 측정 그대로 보존했다.
이번 비교는 그 저장 결과와 최신 실행을 비교한 것이며, 같은 시각에 두 버전을 새로 실행한 A/B 실험은 아니다.
질문과 채점 규칙은 변경하지 않았다. 최신 74턴의 계획과 답문은 원래 결합 후보와 모두 같았다.
처음 재측정한 수정 전 master에서는 럼블/오공 첫 답 하나의 대처 문장이 빠져 있었고 이를 복구했다.

**74/74는 전체 답변 정답률이 아니다.** 자료가 없다는 고지도 올바른 규칙 경로로 분류될 수 있다.
내용 검사는 30개 값·주제 검사로 한정된다. 이전 자체 검토의 자연성 평균을 이번 결과로 재사용하지 않았다.
마지막 15턴도 지금은 기존 질문이라 새로운 미공개 일반화 시험으로 볼 수 없다.

실패한 내용 검사는 이전과 동일하다.

- `s10:0`: 치유 감소 중첩 질문.
- `s13:0`: 치유 감소의 보호막 적용 질문.
- `d06:3`: 다른 질문을 거친 뒤 치유 감소 중첩 질문.

이 세 답은 자료 부재를 알리지만 원하는 내용을 제공하지 못한다.

화면의 최종 대화는 수정 후 13개 입력, 이전 상성 팁 표현 수정 후 1개 재입력,

모델 프로토콜의 `loaded`, `judged`, `embedded` 이벤트를 관찰했으며 출력을 대체하지 않았다.
전체 대화 캡처에 로드 1회·판정 3회·검색 임베딩 1회가 있다.
팁 진행과 수치 조회처럼 코드가 바로 답하는 입력까지 전부 모델 추론을 실행한 것은 아니다.

## 자동 점수만으로 놓친 세 문제와 수정

1. **노트로 조립한 일반 상대법의 대처 문장 누락** (`7058cf435`).
   답 은행이 없는 럼블/오공 첫 답에서 위협 설명은 남았지만 간격을 벌리는 행동 지침이 빠졌다.
   노트 요약 모드를 조정해 일반 상대법의 문단을 보존했다.
   74턴 점수는 수정 전후 같았지만 원문 비교에서 차이를 발견했다.

2. **제목 없는 규칙 요약 뒤 지칭이 이전 상성으로 이동** (`ce2d6e595`).
   앞에 상성이 있으면 관통 질문이 짧은 게임 규칙 요약을 선택하는 경우가 있다.
   기억이 본문의 `###` 제목을 찾아 규칙을 기록하므로 제목 없는 요약은 이전 상성을 활성 상태로 남겼다.
   이후 “그거 평타에도 적용돼?”에 럼블/오공 한타로 답했다.
   계획에 규칙 id·제목을 함께 전달하고 본문 서식과 분리해 기억하도록 고쳤다.
   모델을 켠 같은 입력 순서에서 기본 공격의 관통 적용 답으로 바뀐 것을 확인했다.

3. **이전 상성으로 돌아온 일반 팁이 이미 본 칸을 반복** (`1c6b7539a`).
   저장 상태는 남아 있지만 “아까 상성에서 팁 좀”을 순수한 일반 팁 문형으로 인식하지 못했다.
   상성을 가리키는 앞말과 나머지 요청을 구분해 진행 모드를 유지했다.
   한국어·영어·중국어의 복귀 표현과 특정 주제 재조회에 집중 시험을 추가했다.
   수정 후 같은 입력과 실제 새로고침 후 입력에서 소진 안내를 확인했다.

## 실행 조건과 재현

- Chrome DevTools의 격리된 로컬 Chrome에서 앱 모델 동의를 정상 입력했다.
- 앱의 `onnx-community/Qwen3.5-0.8B-Text-ONNX`, `q4`, `models/kev/b3e/model_q4.onnx`와 기존 판정 헤드·문서 벡터를 사용했다.
- 최신 측정은 새 판정·검색 캐시에서 34개 사례를 순서대로 실행했다. 사례마다 기억을 비우고 대화 내부는 계속 유지했다.
- 준비/모델 다운로드는 턴 시간에 포함하지 않았다. 최신 실행의 준비 제한은 180초, 판정 제한은 30초로 기본값이다.
- 첫 준비 조사에서는 로드 제한만 900초로 늘렸다. 판정 제한이나 실패 대체를 숨기지 않았으며, 최종 실행은 기본 제한으로 완료했다.
- 다른 개발 서버가 공유 Vite 의존성 캐시를 바꿔 최적화 모듈이 504를 반환했던 준비 실패는 임시 서버의 캐시 경로를 분리해 해결했다. 제품 코드에는 해당 임시 설정을 넣지 않았다.
- 평가기가 먼저 받은 모델 캐시와 “모델 없이” 상태가 겹친 테스트 준비는 격리된 시험 화면에서 정상 다운로드·동의 절차로 맞췄다.
- 최신 74턴 수행 중 독립적인 코드 검사도 실행했다. 시간 수치는 로그에 남겼지만 속도 향상 주장에 쓰지 않는다.
  최초 결합 후보의 호출 18회에서 최신 26회로 늘었으므로 호출 비용이 줄었다고도 주장하지 않는다.
- 자유 문장 생성 실험은 이번에 다시 실행하지 않았다. 앱에서 0.8B는 판정·검색, 코드와 준비된 자료는 맥락·답변 조립을 맡는다.

재현은 [기존 질문셋](questions.json)과 `scripts/llm/conversational-advisor/browser.ts`의
`createEvaluation()` → 각 사례의 `runCase(id, "combined")`를 사용한다.
자동 채점은 `score.ts`의 `evaluate(results)`를 사용하며 기존 `scores.json`은 덮어쓰지 않았다.
