# 이름 없는 질문의 자료 찾기 — 벡터 검색 (2026-09-26, 싣지 않음)

챔피언·아이템 이름이 없는 질문("스마 충전 몇 초마다 차?", "how often does a new set of creeps spawn")은 룬·주문·게임 요소
규칙 70 · 게임 원리 9 · 게임 메타 21, 언어마다 100건에서 찾는다. 지금은 낱말로 찾는다(룬·주문 이름 → 게임 메타 낱말 →
게임 원리 낱말 → BM25 + 제목 거르기). 벡터로 찾으면 나은지 쟀다.

- 시험: 720문항(`queries.jsonl`, Claude 에이전트가 작성) — 언어마다 문서 100건 × {바꿔 말하기 1 · 이름 넣기 1} + 답 없는 질문 40.
- 잣대: **맞음** = 답이 있으면 정답 문서를 보였고 없으면 아무것도 안 보였다. **오답 노출** = 틀린 문서를 보였다(가장 해롭다).
  문턱은 절반(문서 id 로 가름)에서 고르고 나머지 절반에서 쟀다. [엄격] = 오답 노출이 지금 앱보다 늘지 않는 문턱.
- 판: 지금 앱(`corpus.ts current`), 0.8B(앱이 받는 Qwen3.5-0.8B q4 + kev 그래프의 `hidden`, 평균·마지막 토큰·요약 프롬프트,
  LoRA 0·1, `embed.py qwen`), 전용 임베딩 multilingual-e5-small(`embed.py e5`, 브라우저 판 q8 약 120MB), 섞은 판(지금 앱이
  못 찾으면 벡터). `score.py` 가 전부 낸다.

## 먼저 찾은 것: 지금 앱의 낱말 찾기 버그 둘 (고침)

| | 맞음 | 오답 노출 |
|---|---|---|
| 고치기 전 | 388/720 | 136건 |
| **고친 뒤** | **396/720** | **82건** |

- `findMechanics` 가 영문 낱말을 부분 문자열로 찾았다 — "da**mage**" 의 Mage, "**ad**ds" 의 AD, "m**id**" 의 id. 영어 질문이
  챔피언 분류 절로 갔다. 영문은 낱말 경계로 바꿨다.
- `hitsToAnswer` 의 제목 거르기가 영어 기능어("the")를 제목 낱말로 쳤다 — "Press **the** Attack", "Walk on **the** water".
  기능어를 빼고 영문은 낱말 경계·대소문자 무시로 바꿨다.

결론: 벡터는 싣지 않는다. 낱말 찾기 버그 둘을 고친 것이 이번에 가장 큰 개선이다. 남은 오답 노출 82건 중 절반은
흔한 낱말이 규칙 이름인 경우("와드 없는 모드에서 킬로 트로피 모으는 룬" → 와드, "피 채워 주는 룬" → 회복)이고,
바꿔 말한 질문은 은어 사전(챔피언 별명 사전처럼, 예: 스마 → 강타)이 더 싸게 잡을 수 있다.

## 개선 둘: 물은 갈래로 좁히기 + 은어 사전 (싣음)

규칙은 dev 절반의 오답만 보고 고쳤고, 은어 사전은 시험 문제를 보지 않은 Claude 에이전트가 롤 지식으로 썼다
(`knowledge/search-aliases.json`, 문서 82건 · 은어 약 400). 사전에서 dev 오답과 기존 374문항(route-large, 대부분 챔피언
질문)을 가로챈 말만 뺐다 — 눈덩이·snowball(스노우볼 굴리기), backing(backing off), 节奏·治疗·终极·秘籍 같은 일상어,
프리징·다이브 같은 넓은 전략 용어(규칙 찾기가 챔피언 찾기보다 먼저라 상성 질문을 가로챈다).

| test 355문항 | 맞음 | 틀린 자료 | 바꿔 말하기 |
|---|---|---|---|
| 낱말 버그 둘 고친 뒤 | 192 | 43 | 13/150 |

전체 720문항: 처음 388 → 447, 틀린 자료 136 → 54. e5 벡터를 섞은 가장 나은 판(test 0.569 · 틀린 자료 0.127)보다
은어 사전 판(0.597 · 0.087)이 낫고 120MB 도 안 든다.

- 물은 갈래로 좁히기(`narrowToAsked`): 질문이 "룬"·"스펠" 이라고 밝혔으면 그 갈래 규칙만. "와드 없는 모드에서 … 룬" 이
  와드로, "피 채워주는 룬" 이 소환사 주문 회복으로 가던 것. 걸린 규칙이 게임 요소뿐이고 게임 메타가 잡히면 메타 먼저.
- 은어: 영문은 낱말 경계, 두 글자 이하 한글은 앞뒤가 한글이 아니거나 조사일 때만("플레이" 의 플 ≠ 점멸).

## 재순위 헤드 — kev 판정기가 후보 중에서 고른다 (2026-09-26, 실험 · 앱 연결 전)

벡터는 "맞는 문서와 틀린 문서의 유사도가 갈리지 않는" 것이 한계였다. 질문과 후보를 **함께 읽고** 고르게 하면 "해당 없음" 을
더 잘 가릴 수 있다. kev 판정기가 원래 하는 일(선택지 중 고르기)과 같은 꼴이라 LoRA·그래프는 그대로(b3-v2) 두고 헤드만 배운다.

- 후보(`candidates.ts`, 모델 없음): 룬·주문 이름·은어 → 게임 메타 → 게임 원리 → BM25(은어를 붙인 문서 100건) 에서 8건 +
  0.8B 요약 프롬프트 벡터 상위 2건(LoRA 끔, 문서 벡터는 미리 계산). 평균 7건, **정답이 후보에 드는 비율 83%**(성적의 상한).
- 선택지 꼴(`rerank_features.py`): `질문: …` 뒤에 "답이 들어 있는 자료를 고르세요" + 후보마다 `제목: 첫 문장 60자` + "해당 없음".
  선택지 끝과 <decide> 의 은닉 상태(LoRA 켬, 앱 판정과 같은 계산), 질문당 약 250토큰.
- 학습(`rerank_train.py`): 학습용 질문 1,980(`train.jsonl`, 시험을 보지 않은 에이전트 셋이 언어별로 작성, 시험과 글자 3-gram
  겹침 0.5 이상 60건 제외). kev-b3i 헤드에서 시작해 헤드만, 씨앗 5개 평균(한 씨앗은 틀린 자료가 31~63 으로 흔들렸다).
  확신 문턱은 학습 자료에서 뗀 검증분에서 (맞음 − 벌점 × 틀린 자료) 가 가장 큰 값. 특징 뽑기는 로컬 CPU 추론(질문당 1.3~1.8초).

1~1.5초 예상), 문서 요약 벡터 파일(100건 × 3언어 × 1024 fp16 ≈ 600KB), 헤드 5개(각 2MB, 평균). 어댑터·특징은
`~/.cache/cooldown-kev/rerank-v1/`.

## 0.8B 임베딩 LoRA

Qwen3.5-0.8B(`Qwen/Qwen3.5-0.8B`, 앱 그래프와 같은 Instruct 가중치)에 LoRA r=16(α 32, kev 와 같은 186곳: 어텐션·MLP·DeltaNet
투영)을 붙여 질문↔정답 문서를 대조 학습했다. 무료 Colab T4, fp32 가중치 + fp16 autocast, gradient checkpointing,
flash-linear-attention.

- 자료: `train.jsonl` 1,980문항을 9:1 로 갈라 학습 1,782(답 있음 1,573)·검증 198. 시험 `queries.jsonl` 은 벡터만 만들었다.
- 손실: InfoNCE, 온도 0.05. 한 걸음 = 한 언어 질문 32개 + 그 정답 문서 + 같은 언어 문서 무작위로 채운 48개(in-batch +
  무작위 음성). 정답이 여럿이면 모두 양성. 답 없는 질문은 손실에서 빼고 문턱 고르기(score.py 의 dev 절반)에만 쓴다.
- lr 1e-4(AdamW, 10% 예열 뒤 선형 감소), 3에폭 147걸음, 한 걸음 약 29초.
- 문서·질문 모두 요약 프롬프트(embed.py 의 EOL 문구, 문서는 제목 + 본문 600자)를 씌워 같은 모델로 벡터를 낸다.

**풀링: 요약 프롬프트 마지막 토큰(eol).** 검증 R@1 — 학습 전 eol 0.34 · 평균 0.13, 1에폭 뒤 eol 0.68 · 평균 0.63(3위 안
0.85 · 0.79). 평균 풀링은 1에폭까지만 돌았다(아래 "막힌 것"). eol 은 2에폭 0.75, 3에폭 0.78 → 3에폭을 골랐다.

  사용자 말투와의 차이도 모른다.

### 앱에 싣는다면

1. **그래프에 LoRA 두 번째 가지.** 지금 그래프(`public/models/kev/b3-v2/model_q4.onnx`, 22.4MB)는 MatMulNBits 186곳마다
   `lora_scale` 로 켜는 kev LoRA 가지 하나다. `scripts/llm/kev-agent/b3/lora_onnx.py` 를 두 adapter 를 받게 고쳐 같은
   186곳에 가지를 하나 더 달고 입력 `embed_scale` 을 새로 둔다. 추가 용량은 LoRA fp16 **21.6MB**(이번에 만든 embed 전용
   그래프가 22.4MB) → 그래프 약 **44MB**. 원본 가중치 `model_q4.onnx_data`(550MB)는 그대로 공유한다. embed 전용 그래프를
   따로 두면 세션이 둘이 되어 550MB 가중치를 GPU 에 두 번 올리므로 안 된다. 두 LoRA 를 하나로 합치는 것은 과제가 달라 불가.
2. **워커 입력.** 생성: 둘 다 0. 판정: `lora_scale` 1 · `embed_scale` 0. 검색: `lora_scale` 0 · `embed_scale` 1, 질문을 화면
   언어의 요약 프롬프트로 싸서 `num_logits_to_keep` 1 로 한 번 돌리고 `hidden` 마지막 자리를 정규화. 질문 하나에 30~60토큰
   prefill 한 번이 더 든다.
3. **문서 벡터는 미리 만들어 싣는다.** 같은 q4 그래프로 300건 × 1024 fp16 ≈ 600KB(언어별 200KB). 코사인 문턱 0.39 밑이면
   "자료 없음"(또는 지금 앱으로 내려가기). 문서 본문이 바뀌면(정적 자료 갱신) 벡터를 다시 만들어야 하므로 갱신 파이프라인에
   ONNX CPU 추론(약 5분)을 넣어야 한다.
4. **싣기 전에 더 잴 것.** 학습에서 뺀 문서로 새 문서 일반화, 실제 사용자 질문 표본, q4 손실을 줄이는 방법(q4 가중치
   위에서 LoRA 를 학습 — 이번에는 fp32).

### 막힌 것·다른 점

- 무료 Colab 세션이 세 번 끊겼다. 처음 둘은 학습 도중(첫 판은 epoch 2·3 결과를 내려받기 전에 잃음), 세 번째는 서버가
  세션을 약 1시간 50분 만에 거두었고 그 뒤로 T4 할당이 `Service Unavailable` 로 거절됐다. 그래서
  - eol 2·3에폭은 1에폭 adapter 에서 이어 학습했다(학습률 일정은 이어 가되 옵티마이저 상태는 새로). 끊기지 않았던 판의
    2에폭 검증 R@1 은 0.80 이었고 이어 학습한 판은 0.75 였다.
  - 평균 풀링은 1에폭까지만 쟀다. 같은 1에폭에서 eol 이 앞서(0.68 대 0.63) eol 로 골랐다.
- CLI 의 로컬 세션 기록이 지워지면(`colab sessions` 에 `[?]`) keep-alive 가 멈춘다. 서버 목록의 `runtimeProxyInfo` 로 기록을
  되살리고 keep-alive 를 다시 띄워 한 번 살렸다.
