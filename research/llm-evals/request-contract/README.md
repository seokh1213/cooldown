# 요청을 유지하는 대화 흐름 평가

## 수용 기준

| 요구 | 구현 / 확인 |
| --- | --- |
| 실제 사람들이 쓰는 표현을 먼저 조사 | `sources.md`; 실제 제목과 변형 질문을 구분 |
| 상성은 1:1, 1:2, 또는 두 독립 1:1 | 최대 두 쌍; 전체 요청이 넘으면 안내하고 일부만 답하지 않음 |
| 과한 수치 비교는 안내 | 10명까지 조회, 11명 이상 또는 전체 챔피언 요청은 줄이는 예시 제공 |
| 질문을 처리하며 다른 요청으로 바꾸지 않기 | 원문·언급 위치를 유지하고 상성 대상은 별도 타입으로 전달 |
| 답변이 요청을 충족하는지 검사 | 상성 대상, 능력치 항목·레벨·대상, 조언을 수치 표로 대신하는 경로 검사 |
| 컨텍스트 / 조건 유지 | 상성별 조건·표시 주제 저장, 수치 조회와 상성 복귀, 저장 복원 시험 |
| 반복 조언 줄이기 | 검증된 문단이 동일하면 공통으로 한 번 표시; 상대 이름 외 나머지가 동일한 문단도 결합 |
| 두 상성 카드와 제목 구분 | 카드 배열을 본문과 함께 전달·저장; 본문 상성 제목은 큰 제목, 조언 항목은 작은 소제목; 두 카드에 각 VS 링크 제공 |
| 실패를 다음 시험으로 옮기기 | 기기 내 평가에 전후 기억·판단·선택 주제·거절 이유 저장; 내보낸 초안의 정답은 사람이 채움 |

## 실행

```sh
node --import tsx scripts/llm/eval-request-contract.ts research/llm-evals/request-contract/after.json
```

32개 시나리오, 41턴. 규칙만 사용하는 `none`과 실제 앱 기본 경로인 `offline`을 각각 실행한다. 대화 사이에는 실제 저장/복원 함수를 거친다. 자료 읽기만 로컬 파일로 대체하고 `answerDialogue` 전체 흐름을 사용한다.

`development` / `heldout` 표시는 작성 시 나눠 둔 개발·회귀용 구분이다. 수정 과정에서 실패 결과를 확인했으므로 맹검 평가가 아니다. 이 질문으로 모델이나 오프라인 분류기를 재학습하지 않았다.

`before.json`은 별도 checkout의 `964065cb4`를 같은 질문·같은 채점기로 실행한 결과다. 판정기가 없는 경로와 있는 경로 모두 비교한다.

마지막 변경 기준 전체 시험 1,688건, 타입 검사·린트·빌드가 통과했다. Chrome의 로컬 앱에서 1:2 첫 답, ‘둘 다 아이템은?’ 후속 질문, 세 상대의 범위 안내, 두 독립 1:1, 기존 공속 비교를 확인했다. 상성 제목은 실제 제목 요소이며 카드 두 장의 VS 링크는 각각 다른 상대를 가리킨다. 카드와 대화 기억의 저장 복원은 별도 시험으로 확인했다.

## 채점 범위

요청한 상성 쌍, 수치 대상·항목, 비교 카드 종류, 좁혀 묻는 예시가 있는 안내, 특정 정의의 근거 문장을 확인한다. **답변 전체의 게임 지식 정확도나 사용자 만족도 점수가 아니다.** 안내만으로 모든 문항을 통과할 수 없도록 상성·조회 문항은 별도 구조 기준을 요구한다.

현재 자료가 지원하지 않는 진행 중 타이머 변경, 도트 피해와 시전자 은신, 딜로스 계산, 서포터 시너지 추천은 답을 만들어 내지 않고 안내한다. 알려진 스킬 효과나 단순 조회까지 거절하지 않는 회귀 시험도 함께 둔다.

## 한계

문장 전체의 의미를 완전히 이해하는 검증기는 아니다. 분류 규칙·오프라인 판정이 놓치는 새 표현은 여전히 생길 수 있다. 기기 내 피드백으로 재현 질문과 전후 맥락을 모아 회귀 시험으로 추가할 수 있도록 했다. 0.8B의 생성이나 실험용 능력치 분류기는 이번 변경에서 활성화하지 않았다.
