# 실제 앱 흐름과 Chrome 확인 — 2026-10-02

## 결론

실험 분류기를 실제 앱의 `answerDialogue`에 연결했다. 기존 오프라인 판정기, 카드와 문장 조립, 대화 기억, 저장·복원을 실행해도 단일 질문 개선은 유지됐다. 여러 턴 개선은 여전히 작았다. Chrome에서 기존 앱과 실험 앱을 직접 입력해 같은 차이를 확인했다.

가중치·개발 기준·평가 문항을 재학습하거나 조정하지 않았다. 분류기는 개발 서버에서 `VITE_STAT_CLASSIFIER_EXPERIMENT=1`일 때만 켜진다. 기본 앱과 배포 빌드에는 실험 분류기를 활성화하지 않았다. 공개 사이트에 푸시하거나 배포하지 않았다.

## 실제 대화 함수 비교

같은 195문항, 8개 대화·36턴, 추가 주제 전환·미지원 레벨·일반어 4개 대화·16턴을 비교했다. 단일 질문은 정해진 이전 기억을 제공하고, 여러 턴은 실제 답변이 만든 기억과 카드만 이어받는다. 매 턴 앱의 `dehydrateTurn → JSON → reviveTurn`으로 저장한 대화를 복원한 다음 질문한다.

| 확인 항목 | 기존 앱 | 규칙 + 자모·문맥 보조 |
| --- | ---: | ---: |
| 단일 질문의 항목·대상·레벨 일치 | 129/195 | 164/195 |
| 8개 대화, 열 순서까지 일치 | 22/36 | 24/36 |
| 8개 대화, 같은 대상의 열 순서는 무시 | 24/36 | 26/36 |
| 추가 주제 전환·미지원 레벨 시험 | 16/16 | 16/16 |
| 다른 질문을 스탯 조회로 오인 | 0/62 | 0/62 |
| 정답인 스탯 답변의 카드 수치·본문 수치·재생 단위 | 모두 일치 | 모두 일치 |
| 저장 복원한 기억 | 모두 유지 | 모두 유지 |

스탯이 아닌 62개 질문의 최종 답변은 두 방식에서 모두 같았다. 이는 기존 답변의 내용이 모두 정확하다는 뜻이 아니라, 새 분류기가 그 경로의 답변을 바꾸지 않았다는 검사다. 모델 동의를 하지 않은 설정이며, `respond`로 남은 질문은 화면과 같은 `withoutConsent` 안내를 기록했다. 0.8B 실행과 생성 품질은 이번 평가 범위에 포함하지 않는다.

표의 열 순서 차이는 오공·제이스의 둘을 제대로 보여줬지만 제이스 열이 먼저 나온 2턴이다. 그 외 실패가 개선된 것으로 세지는 않았다. 전체 조건을 엄격하게 비교한 숫자도 남겨 이전 실험과 비교할 수 있게 했다.

## Chrome에서 직접 확인

기존 앱 6턴, 실험 앱 11턴을 입력했다. `모델 없이 써보기`를 선택했다. 새로고침 1회 후 저장된 대화를 열고 이어 물었다. 화면 기록은 `browser-observations.json`에 저장했다.

| 질문·행동 | 기존 앱 | 실험 앱 |
| --- | --- | --- |
| 체력 → 체력회복량 → 회복량 정정 | 오공·문도 유지, 5초당 3.5 / 7 | 동일 |
| 18레벨에서는? | 5초당 오공 14.55 / 문도 15.5 | 동일 |
| 그럼 공걱속도는? | 오공의 일반 플레이 노트 | 오공 1.04 / 문도 1.05, 18레벨 공격 속도 |
| 문도만 보여줘 | 문도의 일반 플레이 노트 | 문도 1.05, 18레벨 공격 속도 |
| 새로고침 → 방어력은? | — | 문도 108.5, 18레벨 유지 |
| 문도 R 회복량은? | — | R 최대 투여량의 설명과 수치 |
| 체력 물약 회복량은? | — | 물약: 15초에 걸쳐 120 회복 |
| 10명 18레벨 체력 재생 비교 | — | 10개 열과 10개 재생 수치 표시 |
| 이어서 공격속두는? | — | 자료에서 못 찾았다는 안내, 오타 미해결 |

여기서 수치는 웹의 최신 게임 사실을 따로 검증한 것이 아니라 프로젝트에 저장된 패치 26.19 카드와 화면 출력의 일치 여부다.

## 실제 흐름에서 확인한 한계

- `이동속두` 등을 놓치면 다음 레벨 변경에서 예전 항목으로 계속 조회하는 문제가 남는다.
- `체력 회븍량`, 영어 `health regneration`은 기존 규칙이 체력으로 먼저 확정해서 보조 모델을 부르지 않는다.
- 오타 이름과 항목을 동시에 모르는 첫 질문은 상성 노트로 잘못 답할 수 있다.
- 체력 비교 뒤 물약을 물으면 활성 주제가 아이템으로 바뀐다. 이어서 이름 없이 `그럼 기본 방어력은?`이라고 물었을 때 이전 비교 대상이 복원되지 않았다. 이전의 간단한 조회 재생에서는 놓친 앱 경로의 차이다.
- 이름·레벨을 포함해 새 대상을 명시한 주제 전환은 16개 추가 시험에서 유지됐다.

따라서 전통 ML 보조의 단일 질문 개선을 확인했지만, 현재 성적만으로 대화 전체가 충분히 좋아졌다고 판단하지 않는다. 실제 사용자 질문 표본을 새로 모아 평가한 결과도 아니다. 다음 개선 대상은 불확실한 항목 변경의 확인 질문, 다른 주제를 다녀온 뒤 비교 대상 복원, 이름과 항목 오타의 동시 처리다.

## 연결한 코드

- `core.ts`: Node와 브라우저가 같은 특징·자모 분해·가중치 계산·조회 차단 코드를 사용한다. 이전 실험 API는 `runtime.ts`가 유지한다.
- `appClassifier.ts`: 기존 규칙이 조회를 못 만들었을 때 고정 분류기를 호출한다.
- `PlanDeps.inferStatQuery`: 실험용 조회 의존성. 명확한 규칙 조회와 미지원 레벨 안내는 먼저 처리한다. 실험 읽기 실패 시 기존 경로로 이어간다.
- `statPlanForQuery`: 조회의 대상·항목·레벨을 검증하고 기존 카드와 문장으로 조립한다.
- `useAskAdvisor.ts`: 개발 서버의 실험 설정에서만 브라우저 연결을 활성화한다. 가중치는 요청할 때 한 번 읽는다.
- `dataUrl`: Node 대화 평가에서도 자료 URL을 만들 수 있게 개발용 기본 경로를 허용한다. 브라우저·배포본의 기존 BASE_URL은 유지된다.

## 검증

전체 시험 1,604개, 집중 시험 35개, 전체 타입 검사와 변경 파일 린트 통과. 배포 빌드 통과. 기존 772KB 기본 청크의 600KB 초과 안내는 변경 전에도 존재함을 기준 빌드로 확인했다. 새 컴파일·타입·린트 경고는 없다. 배포 자바스크립트에서 실험 가중치 경로와 브라우저 실험 코드가 제외됐음을 확인했다.

`full-flow.json`은 답변·카드 종류·조회·기억·개별 성적을 포함한다. `browser-observations.json`은 Chrome의 화면 기록과 확인 항목을 포함한다. 배포 가중치나 기존 질문셋을 개선된 점수에 맞춰 바꾸지 않았다.

## 재실행

첫 터미널에서 실험 앱:

```sh
VITE_STAT_CLASSIFIER_EXPERIMENT=1 npm run dev -- --host 127.0.0.1 --port 5193 --strictPort
```

두 번째 터미널에서 앱 전체 흐름:

```sh
STAT_APP_BASE=http://127.0.0.1:5193 node --import tsx scripts/llm/stat-classifier/fullFlow.ts
node --import tsx --test tests/data/stat-classifier-app.test.ts \
  tests/data/stat-classifier-experiment.test.ts tests/data/advisor-stat-dialogue.test.ts
npm test
npm run type-check
npm run build
```

기존 앱을 브라우저에서 비교할 때는 실험 환경 변수 없이 다른 포트에서 개발 서버를 실행한다. 첫 6턴은 `conversations.ts`의 `user-report`와 같다. 새로고침·후속 방어력·스킬·아이템·10명 비교·실패 오타는 위 표의 순서로 입력한다. 원시 브라우저 저장소를 직접 읽거나 수정하지 않는다.
