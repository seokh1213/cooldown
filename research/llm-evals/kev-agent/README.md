## A — 대화 상태 (`scripts/llm/kev-agent/eval-a.ts`)

새 문장을 쓰지 않고 있는 문항만 이어 붙인 98대화(`a-set.jsonl`, `build-a-set.ts`).
첫 턴은 route-large 상성 문항, 이어 묻기(F)는 `topicCases` 손 문항에서 챔피언 이름만 지운 것
("다리우스 상대로 라인전 어떻게 버텨" → "라인전 어떻게 버텨"), 새 질문(R)은 route-large 의 다른 문항,
상대 바꾸기(P)는 `topicCases` 의 상대 관점 문항 그대로(정답이 해석에 기대므로 따로 센다).
한 턴은 갈래·내 챔피언·상대·주제가 모두 맞아야 맞은 것이다. 이름을 지우면 주어가 빠져 깨지는 9문항은 뺐다.

## B3 — 판정 칸을 더 잘게, 앱에 연결 (2026-09-25 밤)

"그 밖" 한 칸에 아이템과 게임 규칙이 섞여 있어, 이어 묻기에서 "방어력 올려?"(앞 상성의 이어 묻기)와
"항복 몇 분부터?"(새 질문)를 가르지 못했다. 판정을 나누고 대화 흐름 판정을 더했다. 학습 자료는 전부 코드 틀
문장과 사람이 다시 붙인 라벨이다(토큰 비용 없음).

- 갈래: route-train "그 밖" 258문항을 사람이 item·rune·spell·game·chat 으로 다시 붙였다(`b3/other_labels.py`).
  시험 세트 route-large 의 "그 밖" 75문항도 따로 붙였다(`b3/large_other_labels.py`, `route-large3.json`).
- 대화 흐름(act): "앞에서 M 으로 E 상대법을 물었다" 뒤의 새 말이 followup·more·enemy·mine·flip·new 중 무엇인가.
  틀 문장 1,959(`b3/build_b3.py`, 시험 챔피언 19명 제외). 시험은 손으로 쓴 60문항(`act-test.jsonl`, 세 언어, 틀과 다른 말투).

작은 헤드가 약한 곳(이어 묻기를 새 질문으로, 상대↔내 챔피언 혼동)은 코드가 먼저 가른다(`conversation.ts`):

- 새 질문: 아이템·게임 규칙 문서 이름, 게임 메타 낱말(항복·닷지·LP·정수·가격·스킨·몇 분에 나와 …)만 가른다.
  판정기의 "new" 는 쓰지 않는다. sub-v1 의 game·chat 을 판정기 둘이 동의할 때 새 질문으로 치는 판도 재 봤지만
  이어 묻기를 더 잃었다(손 시험 + 대화 270턴 합계 236 → 뺀 판 240).
- 입장 뒤집기·더 자세히: 문형("입장에서는", "반대로", "왜?", "풀어서", "why", "为什么") → 없으면 판정기.

### 앱에 넣은 것

- `src/lib/advisor/conversation.ts`: 상태(`matchupStateOf`), 판정(`planTurn`·`sideOfNewName`·`actFromWords`), act 질문 꼴.
- `AdvisorPanel.ask` 3단계: 방금 답한 상성이 있고 이번 말의 이름이 하나 이하면 이어 받는다. "앞서 말한 가렌 vs 다리우스 기준입니다" 안내.
- "더 자세히": 미리 쓴 답이면 처음 답에 싣지 않은 칸(`precomputedMore`), 노트 조립이면 물은 칸을 전문으로.
- 판정기 "그 밖" 이 게임 규칙(sub-v1)이고 검색이 비면 모델이 지어내지 않게 "자료에 없다" 고 답한다(`noGameData`).
- 오타 교정 버그: 이어 묻는 말의 낱말이 이름으로 고쳐졌다(그럼·그런→그웬, 나서는→나서스, 자꾸·사야→자야, 나아→나미).
  흔한 첫머리 낱말을 빼고, 상성 대화 중에는 두 글자 낱말을 오타로 보지 않는다.
- 브라우저(모델 없음)에서 "가렌으로 다리우스 상대법 → 그럼 한타 때는? → 다리우스 입장에서는? → 왜? → 피오라는? →
  항복 몇 분부터 돼?" 가 차례로 가렌 vs 다리우스 한타 · 다리우스 vs 가렌 · 같은 쌍의 남은 칸 · 다리우스 vs 피오라 · 새 질문으로 갔다.

## B3 를 브라우저에 — 변경분만 올리고 그래프를 바꿔 끼운다 (2026-09-26)

Hugging Face 에 모델을 새로 올리지 않는다. 원본 가중치(`model_q4.onnx_data`, 550MB)는 지금처럼 onnx-community 에서
받고, **LoRA 를 덧붙인 그래프 파일 하나(22.4MB, LoRA fp16 21.6MB 포함)** 만 우리 사이트(`public/models/kev/b3-v1/`)에서 받는다.

- `b3/lora_onnx.py`: 원본 q4 그래프의 MatMulNBits 186곳마다 `+ lora_scale · (x·Aᵀ)·(Bᵀ·α/r)` 를 붙이고 은닉 상태 출력
  `hidden` 을 더한다. 재양자화가 없다. `lora_scale` 0 이면 logits 가 원본과 정확히 같다(최대 차 0.0).
- 워커: transformers.js 의 사용자 캐시로 `…/onnx/model_q4.onnx` 요청만 우리 그래프로 바꿔 준다. transformers.js 에게는
  `lora_scale` 입력을 숨기고 0 을 채워(생성은 원본 그대로), 판정만 세션을 직접 불러 1 을 넣고 `hidden` 을 읽는다.
- kev 헤드(`public/models/judge/kev-b3`)는 은닉 상태 1024 위의 PointerHead. `?advisorModel=kev` 로만 고른다(시험 중).
- B3 는 Qwen3.5-0.8B-**Base** 에서 학습했는데 앱 그래프는 **Instruct** 변환이다(가중치 대조: Instruct 와 상대 오차 0.082 =
  q4 오차, Base 와 0.094~0.113). 그래도 대화 흐름은 줄지 않았다.

| B3 맥(MLX bf16, Base) | 334 | 52 | — |

반대로 하면? → 피오라는? → 그럼 템은? → 오공으로 하면 좀 나아? → 항복 몇 분부터 돼? → 아리 가격 얼마야?" 가 모두 맞는

  그럴 땐?" 을 새 질문으로 보내 검색 길로 빠졌고, 0.8B 가 "정글은 탑으로 오지 않습니다 …" 를 지어냈다.

  실제 브라우저에서 두 번째 방문에 다시 받지 않는지 확인이 남았다.

- **낱말 패치(지금)는 한국어만 맞춘다.** 영어·중국어 조회는 "자료를 못 찾았다" 로 빠졌다(조회 20 중 12). 낱말 목록이 한국어 위주라는 주석의 수치가 그대로 재현됐다.
- **1 이 지금보다 낮은 까닭**: 갈래 판정기가 "궁 쿨 몇 초야"·"W 쿨타임 알려줘" 를 소환사 주문(spell)이나 스킬 소개(skills)로 가른다(조회 20 중 spellStat 13).
  판정기가 있으면 낱말을 안 보니 낱말이 잡던 한국어 5문항을 잃는다. 모델 없는 기기는 영어·중국어 낱말을 보강해 27 → 32.
- **2 는 구조만 바뀌고 점수는 1 과 같은 이유로 같다.** 기존 특성 시험 73개 기대값 변경 0, 새 문항 4, tsc·eslint·npm test 통과.
  갈래 판정이 `plan.ts` 단계 11곳에서 `understand()` 한 곳으로 모였다(브랜치 `worktree-agent-a9a1b83bdc6a7c275`).
- **3 은 대화 흐름 판정기가 "이 두 챔피언의 수치인가" 를 직접 가르므로 갈래 판정기의 spell/skills 혼동을 비켜 간다.** 낱말 없이 1b 와 같은 33.
  남은 조회 실패 2건은 분류가 아니라 슬롯 읽기다("ult"·"大招" 를 R 로 못 읽음, `detectSlot`). 공략 실패 4건은 기존 동작이다
  (쿨감 아이템 이어 묻기가 "스킬 가속" 규칙 문서로, "闪现交了…" 가 점멸 규칙 카드로).
- 제로샷은 안 된다: 학습 없이 `lookup` 칸만 얹으면 조회 20 중 6.
- **3 의 비용은 A 270 이다.** 한 헤드로 세 판정을 다시 배운 3p 는 240 → 234: 잃은 10턴 중 5는 주제 판정이 흔들린 것(같은 q·k 가 주제도 맡는다),
  4는 중국어 "后期有多强"·"几级开始强" 을 조회로 본 것. 흐름만 새 헤드에 맡긴 3T 는 237 — 남은 −3 은 영어 "tips" 세 턴(더 자세히/이어 묻기 사이)과
  "塞拉斯w蓝耗多少" (상대 챔피언 수치를 이어 묻기로).

### 헤드 재학습 방법과 판

kev 헤드(PointerHead q·k 1024→256)만 이어 배웠다. LoRA 본체는 그대로라 그래프(22MB)를 다시 받지 않고 헤드 파일(1MB)만 바뀐다.

- 자료(`b3/build_lookup.py`): lookup 틀 문장 16×3언어 × 9쌍 = 432, 쿨타임 낱말이 든 공략(followup) 8×3×9 = 216, 기존 act 3,233 을 일곱 칸으로 다시 적음,
  route3 1,391 · topic 600 그대로. 대조(`act_contrast.jsonl` 390): 다른 챔피언의 수치(이름 있음)·룬/주문 쿨타임·게임 규칙·잡담 → new.
  갈래 보강 72: lookup 문장 → spellStat, 공략 문장 → guide. 시험 문장은 쓰지 않았고 시험 챔피언 19명은 틀에서 뺐다.
- 특징(`b3/extract_features.py`): Colab T4 에서 앱 그래프의 판정 위치 은닉 상태를 행당 0.37초로 뽑아 400행 청크로 저장, 로컬이 청크마다 내려받음.
  무료 세션이 두 번 회수됐지만(각 25분쯤) 받은 청크는 남아 다음 세션이 나머지만 이어 뽑았다. 토큰화는 파이썬 `tokenizers` 와 앱 `encodeJudgeRow` 가 5행 모두 같았다.
- 학습(`b3/train_head.py`, 로컬 CPU 4분): 기존 헤드에서 시작, AdamW, 처음 가중치에서 멀어지는 벌점(anchor).

  앱 흐름에서는 이름이 있으면 코드가 따로 가르고 게임 메타는 낱말이 먼저 받아 60/60 이지만, 판정기만의 점수가 내려간다.

### 정리

새 시험은 1b(판정기 OR 낱말)와 3T(흐름만 새 헤드, 낱말은 모델 없을 때만)가 33 으로 같다. 차이는 **판정기가 있을 때 낱말 규칙을 보느냐** 다. 3T 는 보지 않는다.
그 값으로 A 270 −3, 판정기 단독 act 60 −2 를 치른다. 2 는 어느 분류기를 쓰든 필요한 뼈대(가르는 자리 한 곳)이며 회귀가 없다.
헤드는 갈래·주제용과 흐름용을 나눠 두는 편이 안전하다(3p → 3T 가 그 차이). 남은 실패는 분류가 아니라 슬롯 읽기("ult"·"大招")와 규칙 문서 우선 순위다.

#### 배포 뒤 재발 — 검색 벡터의 "새 질문" 검사가 흐름 판정보다 앞에 있었다 (2026-09-30 밤)

배포된 앱에서 같은 질문이 다시 "챔피언 분류" 절로 나갔다. `continueMatchup` 은 이름 없는 말에 대해 `leaveMatchup`(검색 벡터가 자료 하나를 0.55 이상으로

그 앞에서 빠져나가지만, 그 밖의 갈래로 갈리면 벡터가 고른 문서가 답이 됐다. 두 가지를 고쳤다.
