# QA SFT 후속 검증, 2026-10-06

새 한국어 질문에서는 SFT의 개선이 주로 답이 없는 문서에서 거절하는 쪽에 있었다.
정답이 있는 질문의 수치 추출과 실제 앱 검색 이후 응답은 소폭 개선됐다.
현재 문서 카드를 짧은 SFT 답으로 대체할 근거는 부족하다.

## 완료한 범위

- 기존 631개 QA·1 epoch SFT adapter를 그대로 사용했다. 추가 학습은 하지 않았다.
- 새로 작성한 질문 176개와 기존 36개, 총 212개를 현행 LM과 비교했다.
- 학습·dev 문서와 겹치지 않는다. 새 양성 136개는 17개 문서의 68개 사실을 두 번씩
  바꿔 물은 질문이며 독립 표본 136개로 해석하지 않는다.
- 문맥은 질문만 보고 1,300자까지 고른다. 정답·정답 위치를 선택에 사용하지 않는다.
  새 양성 136개 모두 정답 근거 문장이 선택된 문맥에 포함됐다.
- 제공 문서에서의 응답과 실제 `planAnswer`·`hybridSearch` 이후의 응답을 분리했다.
- 배포 q4 기반 가중치와 기존 분류·검색 adapter를 유지한 독립 생성 분기를 만들었다.

## 응답 비교

정답은 숫자·단위·부호·범위를 원문 그대로 답하는 것이다. 공백의 양끝만 제거하고
다른 표기는 같은 답으로 정규화하지 않았다.

| 평가 | 현행 LM | SFT |
| --- | ---: | ---: |
| 새 문맥 제공 질문 전체 | 98/176 | 118/176 |
| 그중 정답 있는 질문 | 82/136 | 85/136 |
| 그중 문맥에 답 없는 질문 | 16/40 | 33/40 |
| 실제 앱이 고른 문서로 짧은 답 생성 | 67/132 | 72/132 |

기존 한국어 36개는 20/36 대 32/36으로 첫 결과가 재현됐다. 그 점수를 새 질문으로
확장하면 전체 55.7% 대 67.0%, 양성만은 60.3% 대 62.5%다. 이전의 88.9%를 전체
실사용 질문의 정확도로 일반화하지 않는다. 답 없는 40개는 같은 문서에서 필드가 없는
질문 20개와 다른 문서를 준 질문 20개로 구성했다.

새 양성의 같은 사실 두 표현을 모두 맞힌 그룹은 현행 33/68, SFT 37/68이었다.
SFT의 새 질문 오류는 오답 숫자 26개, 단위·형식 16개, 답 있는 문서 거절 9개,
답 없는 문서에서 답한 경우 7개였다. 따라서 거절 정책을 강화한 효과와 올바른 값의
선택을 학습한 효과를 분리해야 한다.

## 실제 앱 경로에서 확인한 한계

동일한 동결 앱·자료·분류 헤드·현행 검색 adapter와 문서 벡터를 사용했다.
질문 기록과 화면 챔피언 선택은 비웠다. 양성 중 포탑 방패 보상이 상충하는 4문항은
검색 점수에서 제외해 132문항을 평가했다. 문맥 제공용 음성 질문을 전체 KB의
답 없는 질문으로 간주하지 않았다.

앱은 정답 문서에 112/132 도달했고, 기존 카드·본문에서 정답 문자열이 보인 경우는
110/132였다. 이는 근거 도달·문자열 포함 지표이며 숫자 하나를 정확하게 답한 점수가
아니다. 67/132와 72/132는 같은 앱의 선택 뒤에 붙인 현행 LM·SFT 생성 단계의 점수다.

오경로 20개는 기민함의 '고정 이속'을 고정 CC 문서로, 포탑 체력 회복을 능력치 안내로,
마스터 티어 닷지를 마스터 이 카드로, 부활 시간을 예전 소환사 주문 부활 규칙으로
보내는 사례 등이었다. 정답 문서에 도달한 112개만 보면 생성 정답은 67/112 대
72/112다. 그 문서에서 SFT가 답을 거절한 경우는 7개였다.

숫자·단위가 문서에 그대로 있는지 검사하면 현행 90개 중 67개 정답·23개 오답,
SFT 83개 중 72개 정답·11개 오답이다. 이 검사만으로 질문에 맞는 숫자인지 보증할
수 없다. 예를 들어 기민함의 7%를 물었는데 같은 문서의 0.25초를 고르는 경우다.

## 생성 분기와 속도

새 그래프는 186개 투영에 `qa_scale`을 추가한다. 기존 초기값 1,460개와 외부 q4
가중치 참조가 그대로임을 검증했다. 분류·검색·일반 생성의 실제 특징 18개는 정확히
같았고 기존 SFT 실험 그래프와 한 번의 전체 greedy cached-state 응답이 일치했다.
기존 36개 응답 점수도 재현됐다.

graph 크기는 약 63.1MiB, 추가 adapter는 21,645,312바이트다. 각 요청은 분류
`lora_scale`, 검색 `embed_scale`, 수치 생성 `qa_scale` 중 하나만 켠다.

현재 소스의 워커는 명시적인 `purpose: "grounded-numeric"` 요청에 QA gate만 켜고
최대 24토큰을 생성한다. 완료 전 조각은 흘리지 않고 성공·실패 뒤 gate를 끈다.
QA 분기가 없는 모델이면 해당 요청을 거부한다. 기본 배포 모델을 변경하거나
UI에서 자동으로 이 응답을 보여주도록 켜지 않았다. 브라우저 실측은 아직 하지 않았다.

같은 맥 CPU·ORT 4 threads에서 고정된 질문 12개를 두 번씩 교차 측정했다.
로딩·토큰화·브라우저 시간은 제외했다.

| 후보 | 중앙값 | p95 |
| --- | ---: | ---: |
| 현행 | 0.814초 | 2.957초 |
| SFT 통합 그래프 | 0.803초 | 2.979초 |

이 표본에서 속도는 비슷하다. 이전 비교와 문맥 선택 정책이 달라 이번 교차 측정
내부에서만 비교한다.

## 다음 학습 조건

자연스러운 의미 질문과 여러 숫자가 있는 문서를 학습에 넣어야 한다. 기존 631개는
명시적인 원문 앵커 뒤 숫자 복사가 중심이라 자연 질문의 값 선택, 회·번 단위,
부호가 있는 LP, 복합 분·초와 범위 표기를 충분히 검증하지 못했다.

새 학습용 QA는 기존 train 문서에서 만들고 이번 212개와 그 test 문서는 고정한다.
정답을 말해야 하는 경우와 거절해야 하는 경우의 균형을 별도 dev에서 선택한다.
분류·검색에서 틀린 문서로 가는 20건은 생성 SFT와 따로 다룬다. 브라우저 적용의
조건은 정답 있는 질문의 재현 가능한 개선과 잘못된 숫자 노출의 감소다.

## 재현과 보존

기준 소스는 첫 실험의 동결 스냅샷, source commit `4d6267596bb9ee9f9a35877dce09377574ac1084`이다. 이후의
현재 앱 수정은 비교에 섞지 않았다. 실행은 `sft-followup-20261005-145849`이고 캐시는
`research/.cache/tuning/sft-followup-20261005-145849/`에 있다.

```text
results/provided-summary.json        문맥 제공 결과
results/app-evidence.json            앱이 실제 전달한 근거
results/app-summary.json             앱 검색 후 생성 결과
results/paired-timing.json           통합 그래프 교차 시간
results/*-answers.jsonl              질문별 정답·오류·근거 검사
models/model_q4.onnx                 분류·검색·생성 세 분기
models/model_q4.onnx_data            기존 q4 가중치 hard link
```

명령과 전제는 [실험 도구 README](../../../scripts/llm/tuning/README.md)의 SFT 후속 검증에
있다. 입력 해시가 바뀌면 저장된 결과에서 재개를 거부하며, 각 응답을 로컬 파일에
기록해 중단 시 완료된 질문을 건너뛴다. 이번 후속은 맥 CPU 평가였고 Colab 런타임을
추가 사용하지 않았다. 기존 백업 요구는 유지한다.

검증: Python 집중 테스트 45개, 새 Node 집중 테스트 9개, 앱·scripts 타입 검사,
변경 TypeScript ESLint 통과. Node 테스트에는 실제 generation proxy에 들어간 gate와
분류·검색 직접 요청의 gate, 실패 후 초기화, adapter 없는 모델 거부를 포함한다.
[기계 판독용 결과](comparison.json)에 점수·해시·추론 시간·검증 범위를 담았다.

후속 평가용 로컬 서버·작업자·idle sleep 방지 프로세스는 종료했고 모델·응답·입력은 보존했다.
