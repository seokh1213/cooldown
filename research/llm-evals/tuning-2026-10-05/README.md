다섯 후보와 현행 기준선을 동일한 동결 스냅샷으로 비교한다. 맥에서 분류 헤드 학습,
QA SFT, 실제 앱 평가를 실행하고, Colab T4에서 검색 LoRA와 q4 분류 LoRA를 실행한다.
앱 소스와 배포 모델은 변경하지 않았다. 실험 중 다른 작업에서 수정한 앱 파일은
동결 스냅샷의 평가에 포함되지 않는다.

## 문서 근거 수치 응답

모든 응답은 실제 ONNX q4 모델에서 생성했고, 숫자·단위가 정답과 정확히 같아야
맞은 것으로 채점했다. 질문과 문서가 이미 주어진 평가이며 검색 전체의 점수가 아니다.

| 평가 | 현행 직접 응답 | 두 단계 routing | QA SFT |
| --- | ---: | ---: | ---: |
| 문서 단위로 분리한 합성 질문 120개 | 39/120 | 62/120 | 115/120 |
| 그중 답이 있는 77개 | 21/77 | 19/77 | 72/77 |
| 답이 없는 43개 | 18/43 | 43/43 | 43/43 |
| 별도 자연스러운 한국어 질문 36개 | 20/36 | 14/36 | 32/36 |
| 그중 답이 있는 24개 | 14/24 | 2/24 | 20/24 |
| 답이 없는 12개 | 6/12 | 12/12 | 12/12 |

두 단계 routing은 답이 없는 질문을 거절하는 데 강했지만 자연스러운 질문에서
정답 추출을 많이 놓쳤다. 현재 프롬프트 설정은 채택하지 않는다.

SFT는 631개 QA를 한 epoch 학습했다. train/dev/test는 문서 ID로 분리하고 번역 및
답이 없는 질문의 문맥도 같은 분할에 묶었다. dev loss는 1.1475에서 0.1964로 감소했다.
한국어 36개 중 SFT 오류 4개는 단위 누락 2개와 다른 수치 선택 2개였다.
수치 응답에 대한 유망한 결과지만 자유로운 일반 대화나 전체 RAG 품질로 확대하지 않는다.

SFT 평가 그래프는 기존 classifier LoRA 자리에 SFT adapter를 넣고 생성할 때 그 gate를
켠 실험용 파일이다. 배포하려면 현행 분류·검색 경로를 보존하는 adapter 라우팅 또는
추가 생성 분기가 필요하다. 현행 분류 그래프를 이 파일로 바로 교체하지 않는다.

같은 맥 CPU에서 고정 한국어 질문 12개를 두 번씩 실행하고 세 후보를 번갈아 측정했다.
모델 로딩·토큰화·브라우저 시간은 제외한 ONNX 추론 시간이다.

| 후보 | 중앙값 | p95 |
| --- | ---: | ---: |
| 현행 | 0.818초 | 1.606초 |
| 두 단계 routing | 1.392초 | 2.741초 |
| SFT | 0.781초 | 1.679초 |

SFT의 추론 속도는 이 표본에서 현행과 비슷하다. routing의 추가 호출 비용은 확인된다.

## 검색 기준선과 벡터 갱신

앱의 실제 `hybridSearch`, 고정된 문턱과 lexical/BM25 보정을 사용한다.
문서 벡터 갱신만 한 후보를 분리해 LoRA 학습 효과와 섞지 않는다.

| 평가 | 현행 문서 벡터 | 벡터만 갱신 | 검색 LoRA 학습·벡터 갱신 |
| --- | ---: | ---: | ---: |
| 기존 시험 절반 | 294/355 | 292/355 | 285/355 |
| 현재 문서에 정답 ID가 남아 있는 부분 | 294/349 | 292/349 | 285/349 |
| 별도 실제 질문 목록 | 42/75 | 40/75 | 40/75 |

기존 시험 355개 중 6개의 정답 문서 ID는 현재 자료에서 사라졌다. 시험 원본을 유지하고
호환되는 부분도 함께 보고한다. 별도 75개 질문은 학습 질문과 겹치지 않는다.
이 표는 검색 단계 평가이며, 앞단 개체 라우팅과 화면 답변까지 합친 점수는 아니다.

현행 인덱스는 언어별 100문서, 현재 자료로 다시 만든 인덱스는 언어별 125문서다.
문서 수 증가만으로 기존 질문의 정확도가 올라가지는 않았다.

검색 LoRA의 dev top-1은 76.3%에서 75.3%로 떨어졌고, 시험 절반의 잘못된 문서 응답은
현행 31개에서 42개로 늘었다. 실제 앱 평가에서도 분류·act·흐름은 335/374,
51/60, 58/60으로 같았고, 여러 턴 대화는 221/270에서 219/270,
조회 흐름은 38/39에서 37/39로 떨어졌다. 이번 검색 LoRA 설정은 채택하지 않는다.

## q4 분류 LoRA 파일럿

기존 q4 MatMulNBits의 186개 backbone 투영을 그대로 dequantize해 학습하고,
원래 분류 헤드의 CE loss와 현행 q4 hidden feature의 MSE를 사용했다.
어휘 출력층은 분류에 사용하지 않아 dequantize하지 않았다.

1,120개 전체 학습을 완료한 결과가 아니다. 세션 종료 전에 로컬로 검증해 받은
480개 학습 체크포인트(약 0.429 epoch)를 최종 ONNX q4 그래프로 변환했다.
optimizer·scaler·학습 순서·난수 상태를 보관해 나머지 입력으로 재개할 수 있다.
새 GPU 런타임에서는 이 모델의 시험 요청 1,101개에 대한 hidden feature만 계산했다.
학습을 반복하지 않았고, 로컬 그래프와 GPU 평가 그래프의 SHA-256이 같음을 확인했다.
act와 앱 흐름은 개선됐지만 여러 턴 대화 한 건이 회귀했다. 현행을 일괄 교체할
근거는 부족하다. 1,120개 전체 학습과 별도 검증 데이터의 결과도 필요하다.

## 체크포인트

첫 Colab 런타임이 종료되기 전에 최종 검색 학습 결과를 맥으로 받지 못했다.
그 실행은 완료된 비교로 세지 않고 같은 조건으로 재실행했다.

학습 중 optimizer 업데이트 경계에서 가중치·optimizer·scaler·학습 스텝·난수
상태를 저장하고, 맥의 별도 프로세스가 60초 간격으로 새 체크포인트를 내려받는다.
임시 파일·완료 manifest·SHA-256·안전한 tar 경로 검증을 사용하고, 최근 검증된 사본
3개를 유지한다. 백업한 20스텝을 다시 Colab에 올려 25스텝 이후로 이어지는 것도
확인했다. 맥이 꺼져 있으면 로컬 다운로드도 멈춘다.

실제 Colab 프록시 인증이 만료됐을 때 런타임이 살아 있음을 확인하고 새 접속 정보로
연결을 복구했다. 도구는 이런 인증 만료가 404로 보이는 경우에도 소유권을 확인한 뒤
한 번 재시도한다. 검색 재개 시 배치가 다시 섞이던 문제도 수정하고 남은 질문 순서가
동일한지 회귀 테스트로 확인했다. 수정 후 dev 점수가 처음 실행과 똑같이 재현됐다.

그 뒤 학습 런타임 자체가 종료됐어도 검색 최종 산출물과 q4 480개 학습 체크포인트는
맥에 남았다. 마지막 체크포인트로 모델을 복구해 실제 앱 평가를 완료했다.
평가용 GPU 런타임의 최종 archive도 크기와 SHA-256을 다시 확인한 뒤 자동 종료했다.

실행·복구 방법은 [실험 도구 README](../../../scripts/llm/tuning/README.md)에 있다.
최종 GPU 산출물을 맥에서 검증한 뒤 Colab 런타임을 자동으로 종료한다.

실험 파일은 캐시 경로에 두므로 Git에 학습 가중치나 인증 정보를 추가하지 않는다.
Wukong의 실험 namespace, 두 PVC/PV 및 볼륨 디렉터리, 임시 서비스·프록시,
원격 작업 디렉터리와 실험 Docker 태그는 정리했다. containerd 캐시에는 관리자 권한이
필요해 삭제를 확인하지 못했으며, 공유 이미지나 빌드 캐시는 정리하지 않았다.

현재 가장 유망한 다음 작업은 QA SFT의 평가를 더 넓히고, 현행 분류·검색 경로를
보존하는 생성 adapter 분기를 시험하는 것이다. 나머지 후보는 회귀가 있거나 이득이
작아 서비스 모델의 일괄 교체를 권하지 않는다. DPO는 이번 다섯 후보에 포함하지 않았다.

실험 도구 검증: Python 집중 테스트 30개, Node 집중 테스트 4개, scripts TypeScript
type-check 및 변경 TypeScript 파일의 ESLint를 통과했다.
