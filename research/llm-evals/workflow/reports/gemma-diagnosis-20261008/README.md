# Gemma가 현행 Qwen보다 뒤진 이유, 2026-10-08

**종료 상태, 2026-10-08:** Gemma 실험은 종료했다. 선택 어댑터 사본과 로컬 모델·체크포인트·벡터 백업은 삭제했으며 아래 보존·재현 절차는 삭제 전 기록이다. 현재 상태는 [최종 정리](../gemma-retirement-20261008/README.md)를 따른다.

결론: 이번 Gemma 교체 실패는 모델 이름만으로 설명되지 않는다. **원시 검색의 표현·문서 대응 오차, 기존 검색 보정에 의한 순위 역전, 전역 임계값의 정답 거절**을 실제 입력·파이프라인 개입으로 분리했다. 학습 문서 범위와 길이는 같은 시작 어댑터에서 재학습해 확인했다. 현행 Qwen과 배포 인덱스를 유지하며 이 진단으로 웨이트를 교체하지 않는다.

이 보고서는 **문서 검색과 문서 선택**에 관한 것이다. 전체 챗봇의 생성 답변 정확도, 한국어 일반 능력, Gemma 모델 계열 전체의 성능 결론이 아니다. 이미 결과를 본 질문에 대한 사후 진단이며 새 블라인드 성적표로 취급하지 않는다.

## 비교 기준을 먼저 맞췄다

같은 언어별 192문서와 같은 질문 벡터로 비교했다. 기존 검색 대상 test 316개 중 답이 있는 269개가 아래 분모다. R1은 1순위 정답, R3은 상위 3개 안에 정답이 있는 수이며 검색 보정 전 점수다.

| 모델 | 원시 R1 | 원시 R3 |
|---|---:|---:|
| 현행 Qwen q4, 갱신 문서 | 213/269 | 251/269 |
| 선택 Gemma epoch 1 FP32 | 212/269 | 239/269 |
| Gemma epoch 2 FP32 | **224/269** | 246/269 |

따라서 ‘Gemma가 모든 항목에서 낮다’는 해석은 틀리다. Epoch 2는 R1에서 Qwen보다 11개 많다. 선택된 epoch 1의 R3 격차 12개도 Qwen만 맞힌 23개와 Gemma만 맞힌 11개의 순차이다. 모델별 실제 성공·실패가 다르다.

원래 배포 Qwen의 100문서 R3 261/269를 Gemma의 192문서와 직접 빼면 인덱스 경쟁까지 모델 차이로 센다. 현재 문서와 배포 문서 ID의 **공통 부분은 98개**다. 같은 벡터를 공통 98개로 제한하면 Qwen R3 262/269, Gemma epoch 1은 240/269다. 192개에서는 각각 251·239다. 추가 94문서의 경쟁이 Qwen에서 11개, Gemma에서 1개를 잃게 한다. 이는 공통 98개 부분집합 개입이며 실제 배포 100문서의 재측정은 아니다.

## 1. 원시 검색은 한국어 표현을 문서에 연결하는 데 실패했다

선택 Gemma가 놓친 질문 5개를 골라 같은 뜻을 정식 용어와 명확한 문장으로 다시 표현했다. 문서 벡터·웨이트는 고정하고 질문 벡터만 다시 계산했다.

| 질문 의미 | Gemma 원문→정리한 표현의 정답 순위 | Qwen 원문 순위 |
|---|---:|---:|
| 치감 여러 개의 중첩 | 8→1 | 1 |
| 고정 방어력 감소의 중첩 | 7→1 | 2 |
| 룬 페이지 선택 | 4→1 | 1 |
| 점화 도트 중첩 | 5→2 | 3 |

추가로 ‘CC 걸린 적을 때리는 트루뎀 룬, 공속 올리면 자주 터지나’는 Gemma 6→1, Qwen 원문 3순위였다. 선택 Gemma는 이 **선별된 5개에서 상위 3개 정답 0→5개**, Qwen은 원문에서도 5개다. 실패 사례를 골랐으므로 이를 전체 0%→100% 정확도로 일반화하지 않는다. 문장 명확성·정식 명칭을 함께 바꿨으므로 은어 하나만의 효과라고도 하지 않는다.

이 결과는 용어·표현 대응이 실제 병목임을 보여준다. Qwen 학습 원문에도 ‘치감’, ‘고통스러운 상처’, ‘룬 페이지’, ‘이그’가 없었다. Qwen이 이 별칭을 이번 도메인 학습에서 그대로 외웠다는 설명은 맞지 않는다. Qwen의 사전학습과 넓은 튜닝 중 어느 부분이 이 차이를 만들었는지는 이 입력 개입만으로 나누지 않는다.

원문·정리한 질문과 정답 ID는 [diagnostic-queries.json](diagnostic-queries.json), 순위·점수는 [input-interventions.json](input-interventions.json)에 있다. 앱에 질문별 별칭, 정답 강제, 하드코딩을 추가하지 않았다.

## 2. 기존 앱 보정이 새 질문에서는 정답 순위를 낮췄다

새 test 중 실제 검색 경로에 들어오는 40개는 답이 있는 35개와 무근거 5개다. 같은 벡터에서 BM25·명칭 보너스만 제거하는 반사실 개입을 했다.

| 모델 | 보정 전 R1 | BM25만 | 명칭 보정만 | 현행 보정 모두 |
|---|---:|---:|---:|---:|
| Qwen | 33/35 | 32/35 | 29/35 | 27/35 |
| Gemma epoch 1 | 30/35 | 29/35 | 26/35 | 25/35 |
| Gemma epoch 2 | 29/35 | 27/35 | 26/35 | 22/35 |

현행 가중치는 BM25 0.05, 명칭 보너스 rule 0.5·meta 0.1·mech 0.1이다. 명칭이 질문에 보인다는 이유로 그 문서에 보너스를 주면, 실제 질문의 대상인 원리 문서보다 앞설 수 있다. 예를 들어 점화가 언급돼도 질문 대상은 효과 중첩 원리일 수 있다. 보정으로 인한 순위 역전은 추정이 아니라 같은 벡터에서 재현됐다.

다만 기존 269개에서는 Qwen R1 213→266, Gemma epoch 1은 212→267로 보정이 크게 돕는다. 따라서 **보정을 전부 끄는 해결책도 회귀를 만든다.** 새 문서·원리 질문까지 포함해 보정의 적용 범위나 재순위를 검증해야 한다. 이 문제는 Qwen에도 존재하므로 Gemma와의 차이를 전부 설명하지 않는다.

## 3. 정답을 찾고도 전역 임계값 때문에 거절했다

개발 검증에서만 ‘오답 0, 정답 최대화, 동률이면 높은 임계값’으로 선택했다. 현행 하이브리드 점수의 임계값은 Qwen **0.756871509552002**, Gemma epoch 1 **0.8315876819699619**다.

새 정답 질문 35개에서 Qwen은 1순위 정답 27개 중 **15개를 거절**해 12개만 답한다. Gemma는 정답 25개 중 **20개를 거절**해 5개만 답한다. 무근거 5개의 올바른 거절까지 더하면 최종 정답이 Qwen 17/40, Gemma 10/40이다. 7개 차이는 이 조건에서 순위 차이 2개와 정답 거절 차이 5개로 분해된다. 오답은 각각 6개·5개이므로 거절만 줄인다고 해결되지 않는다.

높은 임계값을 유발하는 개발 검증 오답은 ‘이 룬 쓰면 다음 열 판에서 내가 몇 점 오를지 정확히 말해줘’다. 룬 문서는 관련 있지만 그 근거로 미래 점수를 답할 수 없다. 그럼에도 Qwen 점수 0.726912748969, Gemma 0.813225728429로 높은 관련도를 준다. **관련 문서 검색 점수를 답변 가능성으로 대신 쓰는 설계** 때문에 한 종류의 무근거 질문을 막으려고 다른 주제의 정답까지 전역으로 거절한다.

학습 목표도 이 차이를 설명한다. Gemma의 학습 1,331개는 모두 정답 문서가 있는 질문이다. 손실은 정답 문서를 음성 문서보다 앞세우며, ‘관련 문서는 있지만 요청에 답할 수 없다’는 판정을 직접 학습하지 않는다. 음성 문서와 무근거 질문은 다른 학습 대상이다. 따라서 검색 LoRA를 더 학습시켰다고 답변 가능성 판정도 자동으로 개선될 조건이 아니다.

보정을 모두 제거하고 dev에서 다시 보정하면 신규 40개는 Qwen 정답 24·오답 0·미응답 16, Gemma epoch 1 정답 17·오답 0·미응답 23이다. 둘 다 정답이 7개 늘지만 모델 간 7개 차이는 남는다. 파이프라인 문제와 모델 문제를 구분해야 한다.

## 4. 학습 성공을 비교한 조건도 달랐다

과거 Qwen은 질문을 무작위 분할했다. 평가 대상 300문서, 언어별 100개가 모두 학습 양성 문서로 등장했다. 질문 문자열이 다르더라도 ‘처음 보는 문서에 대한 일반화’ 시험은 아니었다. Gemma는 문서 주제 묶음을 분리해 일부 문서를 양성·음성 학습에서 제외했다.

이번 기존 test 269개를 Gemma 학습 문서 노출로 나누면 다음과 같다. 정답 후보 중 하나라도 해당 언어의 학습 양성에 있으면 ‘노출’이다.

| 모델 | 노출 문서 215질문 R3 | 미노출 문서 54질문 R3 |
|---|---:|---:|
| Qwen | 202/215 | 49/54 |
| Gemma epoch 1 | 196/215 | 43/54 |
| Gemma epoch 2 | **203/215** | 43/54 |

노출 부분에서 epoch 2는 Qwen보다 1개 많다. 남은 격차는 미노출 부분에 집중된다. 다만 문서 난이도·질문 표현도 다르므로 이 집계만으로 인과를 확정하지 않고 아래 같은 예산의 학습 개입을 추가했다.

Qwen과 Gemma의 학습 설정도 같지 않았다. Qwen은 rank 16으로 attention·MLP·DeltaNet 186개 투영, batch 32·문서 48개, 3 epoch, 512토큰, 학습률 warmup·decay였다. Gemma는 attention q/k/v/o rank 8, batch 8, 기존 hard negative 2개, 2 epoch, 문서 256토큰, 일정 학습률이었다. 이 차이는 확인했지만 각각을 독립적으로 바꾸지 않은 상태에서 크기·rank·학습률 하나를 원인으로 단정하지 않는다.

## 5. 문서 길이·학습 범위를 직접 바꿨다

Gemma 학습은 문서 최대 256토큰, 평가는 512토큰이었다. 한국어 192문서 중 **55개**가 256을 넘었고 한국어 학습 448질문 중 **203개**의 정답 문서가 잘렸다. 중국어는 33문서·143/447질문, 영어는 2문서·0/436질문이다. 512를 넘는 문서는 없다.

점화 한국어 문서는 365토큰이며 ‘기존 효과를 덮어쓰고 지속 시간은 갱신되지만 중첩되지는 않는다’는 핵심 규칙이 256토큰 이후다. 정보가 잘리는 현상은 확인됐지만 그것만으로 성능 손실을 증명하지는 못한다. 실제로 **추론 입력만 256으로 맞춘 실험은 큰 차이를 없애지 않았다.** 선택 Gemma의 기존 R3 239→240, 새 R3 69→69다.

따라서 같은 epoch-1 어댑터에서 아래 3개를 사전 고정하고 Colab T4 FP32로 재학습했다. 각 실험은 한국어 448질문·batch 8·56 step, 같은 새 AdamW lr 0.0001·weight decay 0.01, seed·배치 순서·query 최대 256·평가 512를 쓴다.

| 고정 실험 | 학습 문서 길이 | 양성 문서 범위 |
|---|---:|---:|
| length-256 | 256 | 기존 109개 |
| length-512 | 512 | 같은 109개 |
| coverage-512 | 512 | 과거 문서를 포함한 137개 |

마지막 실험은 중복 기존 질문 171개를 과거 질문으로 바꿔 기존 미노출 28문서를 추가했다. 기존 109문서의 질문을 최소 하나씩, 신규 train 39질문을 모두 보존했다. 총 질문·step은 같고 dev/test와 정확히 같은 질문은 0개다. 추가 문서의 질문을 학습하므로 **닫힌 문서 집합의 노출 범위 개입**이며 미학습 주제 일반화 성적이 아니다. 새 질문의 hard negative는 원래처럼 untuned Gemma로 같은 train-family 문서 풀에서 골랐다.

설정은 [diagnostic-protocol.json](diagnostic-protocol.json)에 동결했다. 세 실험을 모두 공개하며 test 점수로 하나를 골라 배포하지 않는다. 한국어만 추가 학습하고 optimizer도 새로 시작했으므로 원래 다국어 epoch 2와 동일한 조건으로 부르지 않는다.

실제 결과는 다음과 같다. 신규 R3는 답이 있는 전체 72개, 신규 최종 정답은 앱 검색 대상 40개에서 각각 dev로 보정한 하이브리드 판정이다.

| 고정 실험 | 기존 R3 /269 | 그중 한국어 /89 | 신규 R3 /72 | 신규 최종 정답 /40 |
|---|---:|---:|---:|---:|
| length-256 | 241 | 82 | 69 | 10 |
| length-512 | 242 | 84 | 69 | 10 |
| coverage-512 | 243 | 82 | 70 | 10 |

**길이를 늘려도 전체 기존 R3는 순증 1개, 신규는 0개다.** 기존에서 3개를 새로 맞히고 2개를 잃었다. 한국어는 순증 2개지만 모든 언어를 합치면 1개다. **문서 범위를 넓혀도 기존·신규 R3는 각각 1개만 늘고 한국어 기존 R3는 오히려 2개 줄었다.** 원래 미노출 한국어 19질문의 R3는 512 비교 양쪽 모두 17/19였다. 따라서 이 예산에서 문서 잘림·문서 노출 범위가 남은 격차의 주원인이라는 가설은 지지되지 않는다. 다른 예산의 장기 학습 효과까지 부정하는 결과는 아니다.

문서 범위 실험은 새 검색 대상 35개에서 원시 R1 29→31, 보정 후 R1 23→26으로 개선됐지만 **최종 정답은 세 실험 모두 10/40, 오답도 모두 5/40**이다. 좋은 순위를 만들고도 전역 임계값에서 이득이 사라졌다. 따라서 이번 상황에서 추가 학습만 반복하는 우선순위는 낮다. 원시 검색 개선과 답변 판정 개선을 별도로 평가해야 한다.

자세한 언어·노출별 결과와 맞힘↔실패 전환 질문은 [controlled-results.json](controlled-results.json)에 있다. 세 모델×1,064질문, **3,192건**의 순위·고정 답변 선택이 실제 앱 하이브리드 함수와 일치했다.

## 모델 선택·구현 의심도 점검했다

원래 trainer dev는 66개, 임계값 dev는 60개다. 장로 드래곤의 대체 정답이 서로 다른 family에 속한 질문 2개×3언어가 후자에서 제외됐다. 첫 정답만 검사하는 학습 dev와 모든 정답을 검사하는 평가 dev의 차이다. 개발 검증 R3 동률에서 R1 50/57 대 49/57로 epoch 1을 선택했지만 실제 하이브리드 dev 정답은 epoch 1 39/60, epoch 2 46/60이었다. **모델 선택 지표와 제품의 최종 목적이 달랐다.** 다만 epoch 2의 신규 오답은 6개로 epoch 1의 5개보다 많아 사후 교체의 근거로 쓰지 않는다.

공식 pinned config와 설치한 Transformers 5.19.0 구현을 대조했다. `task: search result | query:`·문서 title 프롬프트, prompt 포함 mean pooling·정규화, `last_hidden_state` 안의 512→768 투영이 모두 적용돼 있다. 투영층 누락이나 pooling 착오는 아니었다. T4에서 FP32를 사용했으므로 FP16 수치 오류도 아니다. 기본 Gemma q4의 기존 R3 205/269를 FP32로 바꾸면 209/269지만 Qwen 격차는 남는다. **양자화 하나가 이번 실패의 주원인이라는 설명도 맞지 않는다.** 학습 Gemma q4는 측정하지 않았다.

맥에서 공식 가중치의 텍스트 텐서 413개만 받은 부분 모델로도 재생했다. 원본 CUDA FP32의 512토큰 문서 벡터와 최대 절대 오차 약 3.7e-7, 최소 cosine 0.99999 이상을 확인한 뒤 입력 개입에 사용했다. 전체 원본 가중치 SHA를 맥에서 계산했다고 주장하지 않는다. [mac-native-provenance.json](mac-native-provenance.json)에 다운로드·부분 가중치 지문이 있다.

## 다음 개선 방향

웨이트 교체는 보류한다. 실제 확인된 문제에 따라 우선순위는 **문서 확장 시 명칭 보정의 순위 역전과 답변 가능성 판정 분리**, 그다음 **한국어 표현 변형을 포함한 검색 학습과 목적에 맞는 dev 선택**이다. 질문별 정답 규칙을 추가하는 방식은 쓰지 않는다.

검색 모델의 점수 하나를 답변 가능성으로 간주하지 않고, 선택된 근거가 질문의 요구를 충족하는지 판정하는 절차를 별도 검증해야 한다. 문서별 질문 생성, 기존 Qwen 순위의 증류, 기본 모델 표현 보존도 실험 후보지만 이번에 효과를 검증한 것으로 표시하지 않는다. 이번 질문은 회귀·진단으로 편입하고 새 후보 선택에는 별도 미사용 질문을 동결한다.

## 증거와 재현

[diagnosis.json](diagnosis.json)은 5개 모델의 문서 노출별 집계·4개 검색 보정 개입·공통 문서 개입·토큰 잘림·dev 차이를 담는다. [cases.jsonl](cases.jsonl)은 개발 검증·새 검색 대상·모델 간 차이가 난 질문만 보존한다. 원래 점수와 교체 조건은 [이전 보고서](../gemma-tuning-20261008/README.md)를 따른다.

보존 묶음을 풀어 `snapshot.json`, `data/`, 기존 벡터, `official/tokenizer.json`, `frozen-deployed-doc-vectors.json`를 같은 WORK에 두면 다음과 같이 재계산한다. 현재 앱 데이터로 `prepare`를 다시 실행하지 않는다.

```sh
python scripts/llm/gemma-retrieval/diagnose.py WORK OUTPUT
python scripts/llm/gemma-retrieval/diagnostic_score.py WORK CANDIDATES OUTPUT/controlled-results.json
python3 -m unittest discover -s scripts/llm/gemma-retrieval -p 'test_*.py'
uv run --python 3.13 --with numpy --with onnx --with onnxruntime --with torch --with transformers --with peft python -m unittest discover -s scripts/llm/tuning -p 'test_*.py'
```

첫 명령은 CPU 벡터 연산이다. 두 번째는 세 실험의 `vectors.npz` 입력 지문을 검사하고 실제 앱 하이브리드 함수와 질문별 순위·선택 일치를 검증한다. 라이브러리는 원래 [학습 환경](../../../../../scripts/llm/gemma-retrieval/requirements.txt)과 보존된 환경 기록을 따른다. 당시 frozen 학습 소스는 [training-source](training-source/README.md)에 있다. 유지되는 러너는 최종 아카이브 경로만 기존 백업 계약에 맞췄으며 학습 텐서를 변경하지 않았다.

## 복구·보존·검증

학습 중 첫 Colab 할당이 사라졌다. 양쪽 길이 실험은 56 step까지, 문서 범위 실험은 13 step까지 맥에 검증돼 있었다. 같은 T4·torch 2.11.0+cu130·FP32 환경에 original source·입력 지문·optimizer·RNG·완료 결과를 복원했다. 반복된 20·30 step loss의 차이는 각각 약 5.96e-7이었다. 완전한 비트 단위 재현으로 주장하지 않는다. [interruption-recovery.json](interruption-recovery.json)에 남겼다.

문서 범위 체크포인트에서 앞의 두 완료 실험도 복원됐다. 두 실험의 최종 어댑터·벡터·summary는 끊기기 전 백업과 바이트 단위로 같다. 길이 실험의 완료 시간은 174.5초·279.2초이며 문서 범위 summary의 238.8초는 재개 구간만 잰 시간이다. [first-runtime-summaries.json](first-runtime-summaries.json), 두 런타임의 [step 기록](training-progress.jsonl), [최초 환경](first-training-environment.json)·[복구 환경](recovered-training-environment.json)에 기록했다.
