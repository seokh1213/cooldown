# EmbeddingGemma 2 로컬 검색 비교, 2026-10-08

결론: 현행 Qwen 검색 LoRA를 유지한다. Gemma는 CPU 질문 임베딩이 약 4.6배 빠르지만, 문서 회수율과 관련 없는 후보 노출이 나빠져 사전 WebGPU 진입 기준을 통과하지 못했다. 모델·검색 벡터·서비스 설정은 교체하지 않았다. WebGPU는 실행하지 않았다.

## 비교 조건

- 대조군은 master `65412a297`의 QA+검색 그래프, 검색 gate만 1. 배포 문서 벡터는 언어별 100개다.
- 현행 문서를 다시 추출하면 언어별 192개다. 기존 ID 2개가 없어졌고 신규 ID 94개가 추가됐다. Qwen과 Gemma 모두 이 192개로 새 벡터를 계산해 모델 차이와 인덱스 차이를 구분했다.
- Gemma는 텍스트 q4, 768차원. 공식 검색 접두어와 BOS/EOS를 사용하며 이미지·동영상·음성 특징은 `[0, 512]`로 넣었다. 별도 미디어 인코더는 받지 않았다.
- 짧은 본문: 양쪽 모두 문서 본문 600자, 최대 512토큰. 추가 Gemma 변형은 본문 전체, 최대 2,048토큰이다. 질문·문서 내용은 동결 입력에 보존했다.
- 새 후보의 답변 임계값은 dev에서만 선택했다. 오답 상한은 현행의 dev 오답 수이며, 정답 최대·오답 최소·높은 임계값 순이다. 두 Gemma 변형 선택도 dev만 사용했다. 동률이면 짧은 입력을 선택한다.
- 실제 앱의 BM25 상위 100개, `lexicalHit`, `hybridSearch`, 검색 경로 제외 조건을 사용했다. 빈 화면·빈 대화 기준이며 명시적 몬스터의 코드 응답 경로도 제외한다.

원본 720문항은 문서 ID CRC32로 dev 365 / test 355로 나눈다. 현재 문서에서 사라진 정답 ID의 12문항을 격리하고, 실제 검색 경로 밖인 질문도 제외하면 **dev 337 / test 316**이다. 이 316문항은 답 있음 269, 답 없음 47이다. 옛 355문항 점수와 경로 밖 결과도 `scores.json`에 함께 남겼다.

## 주 평가: 문서 선택

정답은 정답 문서를 선택했거나, 답이 없는 질문에서 답변을 내지 않은 경우다. 관련 후보 노출은 별도 집계한다. 챗봇 전체 답변의 사실 정확도를 뜻하지 않는다.

| 설정 | 정답·보류 / 316 | 잘못된 답변 | 답 있는 질문의 정답 / 269 | 벡터 R@3 / 269 |
|---|---:|---:|---:|---:|
| 현행 Qwen, 배포 100개, 임계값 0.43 | 305 | 10 | 268 | 261 (97.0%) |
| 같은 Qwen, 현행 192개, 임계값 0.43 | 303 | 10 | 265 | 251 (93.3%) |
| Gemma, 192개·짧은 본문, dev 임계값 0.7932151198387146 | 307 | 4 | 263 | 205 (76.2%) |
| Gemma, 192개·전체 본문, 같은 dev 임계값 | 307 | 4 | 263 | 204 (75.8%) |

Gemma 합계 +2건은 답 없는 질문을 더 많이 거절한 결과다. 답 있는 질문의 성공은 268→263건으로 감소했다. 쌍별 비교는 양쪽 정답 299, Qwen만 정답 6, Gemma만 정답 8, 양쪽 실패 3이다. 뚜렷한 품질 향상으로 해석하지 않는다.

임계값을 현행 0.43 그대로 쓰는 Gemma는 **268/316, 잘못된 답변 48건**이다. 단순 웨이트 교체는 불가능하다. 답변 임계값을 보정해도 후보 제시 임계값 0.35는 남아 있어, 답 없는 질문에 관련 없는 후보를 보여주는 수가 **5→44건**으로 늘었다.

## 다른 표본

- 기존 직접 질문: 검색 경로의 18문항은 현행·Qwen 재계산·보정 Gemma 모두 18/18이다. 전체 원본은 26문항이다.
- 기존 실제 말투: 검색 경로 33문항에서 현행 21정답·11오답, 보정 Gemma 21정답·12오답. 전체 원본은 75문항이며 일부 답 없음 라벨이 오래됐다.
- 신규 문서 12개에 대한 한국어·영어·중국어 36문항을 결과 확인 전에 작성했다. 검색 경로는 35문항. Qwen 재계산은 27정답·7오답, 보정 Gemma는 22정답·8오답이었다. 동결된 dev 임계값을 그대로 사용했고 이 표본으로 튜닝하거나 모델을 선택하지 않았다. 영어·중국어 질문의 한국어 번역은 `qKo`에 있다.
- 배포 100개 인덱스에는 신규 문서 ID가 없으므로 이 표본에서 정답 ID 회수는 0이다. 이 수치는 챗봇 전체의 답변 성공률을 뜻하지 않는다.

**라벨 한계:** 기존 시험은 검색 LoRA가 학습한 문서에 대한 과거 질문이다. 새 192개 문서 중 같은 사실을 설명하는 다른 문서도 있어서, 의미상 맞는 대체 문서를 ID 채점이 오답으로 볼 수 있다. 신규 표본도 에이전트 작성 진단이며, 실제 사용자 트래픽이나 독립적인 새 사실 36개로 해석하지 않는다. 원본 라벨을 결과에 맞춰 바꾸지 않았다.

## CPU 비용과 크기

Apple M2 Pro, RAM 32GiB, ONNX Runtime CPU, 4스레드, batch 1. 문서·질문 벡터 생성은 병렬로 했고, 아래 속도는 모든 생성이 끝난 뒤 두 모델을 분리해 같은 질문 60개·문서 15개로 측정했다. 다운로드와 최초 적재는 질문 시간에서 제외했다.

| 모델 | 질문 중앙값 | 질문 p90 | 전체 벡터 생성의 프로세스 최대 RSS | 분리한 속도 시험의 최대 RSS |
|---|---:|---:|---:|---:|
| Qwen | 131.6ms | 157.0ms | 1,782.9MiB | 1,327.1MiB |
| Gemma 짧은 본문 | 28.7ms | 35.7ms | 915.6MiB | 647.8MiB |
| Gemma 전체 본문 | 28.8ms | 35.2ms | 1,128.7MiB | 774.9MiB |

Gemma 파일 추가 다운로드는 206.70MB다. 현재 설정의 Qwen 610MB에 더하면 약 816.70MB이며 브라우저 RAM 측정치는 아니다. 답변 생성용 Qwen이 계속 필요하므로 Gemma 프로세스의 RSS가 작다는 이유로 챗봇 전체 메모리가 줄어든다고 볼 수 없다.

## WebGPU 판단

결과를 보기 전에 정한 조건: 주 시험 정답 최소 +1, 오답 증가 0, 벡터 R@3 감소 0, 직접 질문 퇴보 0, CPU 질문 p90 ≤2초, 최대 RSS ≤4,096MiB, 합산 다운로드 ≤1,000MB. **R@3 조건 실패**로 다음 단계에 진입하지 않았다. CPU 결과를 WebGPU 실측으로 표기하지 않았다.

## 재실행

프로젝트 의존성과 `uv`가 있는 환경에서:

```sh
npm run llm:test:embeddinggemma -- \
  --cache research/.cache/embeddinggemma2 \
  --out research/.cache/embeddinggemma2-report
```

현행 문서 추출 → 고정 revision·SHA-256 모델 준비 → 세 CPU 인코딩 → 분리한 속도 측정 → dev 선택·test 채점 → 신규 문서 진단 → 앱 함수와 선택 일치 검증 → 작은 증거 보존을 순서대로 실행한다. 실행기는 로컬 비교용이며 WebGPU를 자동 실행하지 않는다.

임베딩은 25행마다 원자적으로 저장하며 같은 입력·그래프·토크나이저·실행 코드일 때 재개한다. 평가와 모델 소스가 바뀌면 새 캐시 경로를 사용한다. 가중치 캐시는 보고서에 복사하지 않으며, 필요 없어진 실행 캐시는 사용자가 지정한 해당 경로만 정리한다.

`llm:test --profile infrastructure`와 `quality`에는 이번 평가 도구의 집중 단위 검사가 포함된다. 대형 비교는 명시한 위 명령으로 실행한다. 현재 결과의 동결 입력은 `snapshot.json.gz`와 `probe-snapshot.json.gz`, 원본·모델 해시는 `models.json`, 쌍별 결과는 `predictions*.jsonl`이다. `retention-manifest.json`은 보존 파일의 SHA-256을 기록한다.

다음 개선 후보는 모델 교체보다 문서·검색 인덱스의 동기화와 중복 문서 평가 라벨 정리다. 단순 192개 재계산도 기존 시험을 305→303건으로 낮췄으므로 바로 배포하지 않았다.
