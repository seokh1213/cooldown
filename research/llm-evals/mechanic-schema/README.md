# 패시브 규칙 JSON v1 실험

## 결론

파이크·아크샨의 선택된 패시브 규칙을 고정 스키마로 만들고 코드로 판정하면, 이번 소규모 질문셋에서는 후속 대화·조건 변경·체력 전환 계산이 개선됐다. AI가 규칙이나 질문 조건을 추출하는 품질은 별도로 확인해야 한다. JSON 형식 강제만으로 내용 정확성까지 보장되지는 않았다.

2026-10-04, 데이터 패치 26.19, 로컬 Node와 Ollama Qwen3.5 0.8B Q8_0으로 실행했다. 앱 기본 답변 경로·브라우저 q4·배포본에 연결하지 않은 연구 실험이다.

## 결과

기존 질문 26턴과 새로 작성한 진단 질문 12턴, 합계 38턴을 실행했다. 이 중 근거 답변 36턴과 연구 범위 안내 2턴을 따로 평가했다. 새 질문은 독립적인 모집단 표본이나 맹검 홀드아웃이 아니다. 이 작성자가 준비한 사례에서의 결과이며, 전체 챔피언·모든 표현에 대한 정확도로 일반화할 수 없다.

| 방식 | 근거 답변 통과 | 중앙 응답/추출 시간 |
|---|---:|---:|
| 기존 앱 `answerDialogue` + 오프라인 판정기 | 18/36 | 약 9ms |
| 공통 질문 단서로 조건 추출 + 검수한 JSON + 코드 판정 | 36/36 | 약 1ms |
| 0.8B JSON 조건 추출 + 동일한 JSON + 동일한 코드 판정 | 9/36 | 추출 약 1.21초 |

마지막 방식의 추출 JSON은 **36/36 형식 검증을 통과**했다. 그러나 주제·대상·추가/기본 구분·수치를 잘못 추출했다. 예를 들어 체력 양을 말하지 않은 질문에 `healthAmount: 800`을 만들어 넣었다. 주제에 적용되지 않는 필드는 기억 갱신 시 제거되지만, 잘못 추출한 해당 주제의 필드는 여전히 답변을 바꿀 수 있다.

사실 판정은 모델 생성 문장이 아닌 공통 코드가 한다. 9/36이라는 값은 조건 추출이 틀린 경우까지 포함한 최종 답변 점수다. `query-results.json`의 문자열 자동 채점은 보조용이다. `14`가 소수 `57.1429` 안에 있어 통과하는 초기 채점 문제를 수정했고, 숫자를 요청하지 않았는데 가상의 수치를 넣은 답도 탈락시켰다. 원문 수동 검토를 기록한 **`audit.json`이 최종 지표**다. 기존 답변은 조건이 원문에서 명확하게 설명되면 직접적인 부정 문장 없이도 인정해, 새 템플릿에 유리한 문자열 일치로 채점하지 않았다.

아리처럼 미구조화한 챔피언과 여러 챔피언을 한꺼번에 묻는 2턴에는 연구 범위를 안내했다. 이 두 안내는 36턴의 사실 점수에 넣지 않았다. 기존 앱의 여러 챔피언 지원을 제한하거나 우열을 평가한 실험도 아니다.

### 실제 대화 예시

| 질문 | 기존 답변 | JSON과 코드 판정 |
|---|---|---|
| 파이크 체력 140짜리 템이면 공격력 얼마나 받아? | 체력 14당 공격력 1이라는 원문만 제시 | 추가 공격력 10, 최대 체력은 그만큼 늘지 않음 |
| 체력 140 받으면? → 아니 280짜리면? | 기본 체력 조회 → 운용 노트 | 추가 공격력 10 → 20으로 정정 |
| 아크샨 평타 한 대 → 두 번째까지 다 치면? | 패시브 → 운용 노트 | 취소 시 이속 → 끝까지 발사하면 해당 이속 없음 |
| 미니언에게 세 대 → 챔피언이면? | 미니언 규칙 → 운용 노트 | 미니언 보호막 없음 → 3번째 적중·챔피언·보호막 쿨 조건 보존 |
| 기본 체력도 공격력으로 바뀌어? | 기본 스탯 조회 | 기본·레벨 성장 체력은 전환하지 않음 |
| 아크샨 쉴드 쿨 남았는데 챔피언 세 대? | Q/W/E/R 쿨타임 목록 | 추가 피해 조건 설명, 보호막은 쿨이 남아 발동하지 않음 |

### 규칙 자동 작성 실험

같은 v1 스키마를 사용해 원문으로부터 0.8B가 규칙 후보를 쓰게 했다. 기본 프롬프트는 각 챔피언 3개 seed, temperature=0.4로 6회 실행했고, 숫자 예시를 뺀 짧은 프롬프트로 2회를 추가했다.

* 규칙 후보 8개 중 완전한 스키마 검증 통과: **4/8**.
* 검수한 규칙과 조건·수치·범위까지 일치: **0/8**.
* 파이크의 전환 방향을 뒤집거나 전환 분모 0을 만들고, 아크샨에 체력 전환을 추가하거나 피해 유형·감쇠 시간을 틀렸다.
* 생성된 필드 이름은 허용된 형태를 따랐지만, 수치 범위까지 강제되지 않았다. `inputPerOutput > 0` 같은 제약은 실행 전 검증에서 다시 잡았다.
* 후보는 모두 `candidate`로 남겼다. `reviewed-records.json`에 자동 반영하지 않았다.

질문 추출도 같은 스키마에 숫자 예시 없는 짧은 영어 프롬프트를 넣어 8턴 재시험했다. 형식 8/8, 내용 1/8이었다. 초기의 불필요한 숫자는 줄었지만 주제/조건 오류는 남았다. 언어와 길이도 바꾼 대조이므로 숫자 예시 하나만의 인과 효과라고 해석하지 않는다. 이번 설정에서는 형식을 고정하는 것만으로 안정적인 질문 해석을 얻지 못했다.

총 실제 모델 생성 호출은 **52회**다: 첫 질문 추출 36회 + 규칙 후보 6회 + 단순화한 질문 추출 8회 + 규칙 후보 2회. API 오류나 검증 실패를 기존 답변으로 바꿔 모델 성공으로 집계하지 않았다.

## 고정 계약

정의는 `scripts/llm/mechanic-schema/schema.ts`의 JSON Schema에 있고, 생성 제약과 실행 전 Ajv 검증에 같은 객체를 쓴다. 덤프한 `*.schema.json`은 공유·검토용 산출물이다. Ollama의 `format` 지원은 [공식 문서](https://docs.ollama.com/capabilities/structured-outputs)를 확인했다.

* `schemaVersion: 1`: 필드 의미·단위·기억 병합 정책이 바뀌면 버전을 올린다. 이전 버전을 조용히 새 의미로 해석하지 않는다.
* 알 수 없는 키, 필드 별칭, 허용 목록 밖의 효과/스탯, 누락된 필수 키, 숫자 문자열은 거절한다. 값 보정·형변환·기본값 삽입은 하지 않는다.
* 규칙은 `stat_conversion`, `followup_attack`, `stat_buff`, `damage_proc`, `shield`, `damage_storage`, `recovery`의 7종류다. v1은 같은 유형을 한 패시브에 한 번만 허용한다. 여러 변형이 필요한 챔피언은 계약 확장이 필요하다.
* 비율은 배수로 저장한다. `800% = 8`. 전환의 `inputPerOutput: 14`는 추가 체력 14당 추가 공격력 1이다. 단위는 스탯/효과 종류가 정한다.
* `null`은 **이번 질문에서 명시하지 않음**이다. `false`는 명시적인 부정이므로 지우거나 null로 바꾸지 않는다.
* `from: bonus_max_health`는 아이템 등에서 얻는 추가 최대 체력이다. 기본 체력과 레벨 성장 체력은 이 입력에 포함하지 않는다.
* `scope: same_target`의 적중 횟수는 동일 대상의 중첩이다. 공격 명령 횟수와 모든 대상의 적중을 합친 값으로 취급하지 않는다.
* “평타 한 대”만으로 후속 공격을 취소했다고 추측하지 않는다. 조건이 없으면 두 번째 공격과 취소 시 이속을 함께 설명한다.
* 보호막 쿨이 알려지지 않으면 쿨이 준비되어 있어야 한다는 조건을 문장에 남긴다. 한 번 적중 질문은 처음부터 중첩을 쌓는 경우로 한정해서 설명한다.
* 챔피언·주제·패치·스키마 버전이 바뀌면 해당 범위를 벗어난 가정을 지운다. 같은 주제의 대상/수치 정정은 다른 가정을 유지한다.

### 메타데이터와 출처

`champion`, `slot`, `patch`, `schemaVersion`, `source`, `reviewStatus`는 코드/검수자가 관리한다. 생성 모델에는 규칙 `rules`만 작성하게 한다. `reviewStatus`를 AI가 승인으로 바꾸게 하지 않는다.

`source.sha256`는 승인 당시 원문의 요약·본문·기존 CC 데이터 해시다. **저장된 승인 해시를 실행 때 최신 해시로 덮어쓰지 않는다.** 원문이 달라지거나 패치가 바뀌면 `needs_review`가 되어 답변을 보류한다. 새 원문을 확인해 규칙을 수정·검수하고 새 해시로 승인하는 단계가 필요하다.

`coverage: partial`을 명시했다. 수치 곡선, 3타 중첩의 만료 시간, 추가탄 피해량과 미니언 예외, 회복 비축 한도의 모든 제한 등은 구현하지 않았다. 규칙이 없다는 이유만으로 효과가 없다고 단정하지 않는다. 기절 부정은 기존의 `known` CC 기록이 비어 있음을 별도로 확인한 범위에서만 답한다.

영문 26.19 카드가 주 출처다. 앞선 실험에서 한국어 아크샨 요약의 피해 유형과 파이크 본문의 추가/전체 체력 표현이 충돌했던 문제를 피했다. 직접 확인한 자료:

* [라이엇 파이크](https://www.leagueoflegends.com/en-us/champions/pyke/), [위키 파이크 상세](https://wiki.leagueoflegends.com/en-us/Template%3AData_Pyke/Gift_of_the_Drowned_Ones)
* [라이엇 아크샨](https://www.leagueoflegends.com/en-us/champions/akshan/), [위키 아크샨 상세](https://wiki.leagueoflegends.com/en-us/Template%3AData_Akshan/Dirty_Fighting)

위키 페이지 직접 열기는 robots/cache 제한이 있었고 검색에 반환된 과거 수집 내용과 로컬 패치 자료를 대조했다. 라이엇 페이지는 현재 직접 열어 확인했다. 숨은 상호작용을 모두 최신 클라이언트에서 검증한 자료는 아니다.

## 실행과 파일

```sh
node --import tsx --test tests/unit/mechanic-schema.test.ts
node --import tsx scripts/llm/mechanic-schema/run.ts
node --import tsx scripts/llm/mechanic-schema/refine.ts
node --import tsx scripts/llm/mechanic-schema/audit.ts
```

Ollama 로컬 서버와 `qwen3.5:0.8b`가 필요하다. 마지막 `audit.ts`의 수동 판정 목록은 이번에 읽은 출력에 대한 것이므로, 다른 모델/프롬프트로 다시 실행했다면 출력 재검토와 판정 갱신이 필요하다.

* `reviewed-records.json`: 승인 해시를 고정한 두 패시브 규칙.
* `rule/record/query/memory.schema.json`: 고정 필드와 허용값.
* `cases.json`: 실행 전 정한 질문과 자동 확인 항목.
* `query-results.json`: 기존 답변, 코드 추출, 실제 0.8B 원문과 기억/판정 결과.
* `author-results.json`, `refined-results.json`: 실제 후보 JSON, 원문, 검증 실패.
* `audit.json`: 수동 판정 목록·최종 점수·속도·호출 수.

검증: 집중 단위 시험 18건, scripts TypeScript 검사, 변경 파일 ESLint 경고 0. 연구 코드의 공통 판정기에는 챔피언 이름별 답변 분기가 없다. 이름 탐지는 앱 함수를 사용한다. 현재 코드 추출기는 공통 단서 규칙이라 표현 범위가 제한적이며, 앞으로 오타·복합 질문·새 표현에 대한 독립 표본 시험이 필요하다.

## 요청 확인

| 요청 | 확인 |
|---|---|
| 필드·허용값·단위부터 고정 | JSON Schema v1, 알 수 없는 키/별칭/형변환 금지 시험 |
| 파이크·아크샨 구조화 | 선택 범위의 7개 규칙과 출처/검수 메타데이터 |
| 실제 단일·여러 턴 비교 | 38턴 진입점 실행과 52회 실제 로컬 모델 호출 |
| 대화 조건 코드 유지 | 대상/수치 정정, 주제/챔피언 전환, JSON 기억 복원 시험 |
| 패치 변경 유지보수 | 고정 원문 해시/버전 차이에서 재검수 보류 시험 |
| AI 생성 일관성 | 8개 규칙 후보 반복 생성, 형식 검사와 내용 검수 구분 |

다음 도입은 검수한 규칙과 코드 판정을 기존 앱에 연결하고, 미지원 질문은 기존 흐름으로 넘기는 방식이 적합하다. 0.8B가 매 질문마다 규칙 JSON을 새로 작성하게 하는 방식은 이번 결과로 채택하지 않는다. 상위 모델이 자료를 정리하더라도 같은 후보 스키마와 출처 검수를 거쳐야 한다.
