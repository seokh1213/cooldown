# 낮은 확신을 0.8B로 넘기는 시험

최신 결과는 [실제 앱 Q4 보완 검증](browser-q4.md)에 있다. 낮은 확신 보완과 구조 검사를 운영에 연결했고, 같은 대화에서 27→31/33이었다. 아래는 운영 연결 전에 로컬 Ollama로 비교한 기록이다.

[두 판정의 불일치를 다시 묻는 후속 시험](dual-review.md)도 마쳤다. 같은 질문에서 일반 74/99, 정정 29/36, 대화 14/33으로 기존 혼합 방식보다 나빴고, 운영 적용을 보류했다.

## 0.8B 단독과 같은 조건으로 비교

하이브리드의 마지막 설정과 시스템 지시, 전체 후보 11개, 같은 언어의 예시 15개, 모델 digest 및 생성 설정을 그대로 유지하고 모든 요청을 처음부터 0.8B로 판정시켰다. 로지스틱 후보·점수·시험 정답은 모델 입력에 포함하지 않았다. 추가 프롬프트 조정이나 학습은 하지 않았다.

| 방식 | 일반 / 99 | 부정·정정 / 36 | 실제 대화 처리 / 33 |
| --- | ---: | ---: | ---: |
| 현재 문자 판정기 및 앱 경로 | 75 | 20 | 27 |
| 낮은 확신만 0.8B로 보완 | 82 | 28 | 28 |
| 처음부터 모든 요청을 0.8B로 판정 | 68 | 28 | 15 |

단독은 일반 질문에서 혼합 방식의 오답 3개를 고쳤지만, 맞던 질문 17개를 틀렸다. 예를 들어 “기본 공속 수치가 몇이지”를 전체 능력치, “R 스킬정보 알려줘”를 전체 스킬로 넓혀 잡았다. 한국어·영어·중국어 일반 질문은 각각 23/33, 24/33, 21/33이었다. 부정·정정은 두 방식의 선택이 모두 같았다.

실제 대화도 세 정책을 한 실행에서 다시 비교하고 턴마다 저장·복원을 거쳤다. 단독은 Q/W/E/R 하나를 묻는 15턴 전부를 전체 스킬로 보내 실패했다. 혼합 방식 대비 2턴을 고치고 15턴을 깨뜨렸다. 단독에서는 요청 로지스틱을 호출하지 않으며, 인터페이스의 `confidence: 0`은 확률이 없다는 표시로만 쓴다. 이 값은 계획기의 분기 기준으로 사용되지 않는다. LLM은 현재 질문만 판정하고 대화 기억은 기존 코드가 처리한다.

135개 범위 판정에서는 혼합 방식이 모델을 부른 72개 요청의 입력 해시와 출력이 단독 결과와 모두 일치했다. 실제 대화에서는 혼합 6/33턴, 단독 33/33턴에 LLM을 호출했다. 캐시는 모델 digest와 요청 본문으로 식별하므로 동일 호출은 재사용했다. 캐시를 포함한 이번 실행 시간을 추론 속도로 보고하지 않는다.

이 설정과 시험 자료에서는 단독 교체를 추천하지 않는다. 이전의 불균형 예시 프롬프트로 얻은 55/99와 이번 68/99를 구분한다. 0.8B 자체의 한계를 입증하는 결과는 아니며, 소규모 수작업 질문과 고정 프롬프트의 결과다. LoRA 학습 및 브라우저 Q4·kev 그래프의 성능은 이 시험에서 확인하지 않았다. 결과는 `standalone.json`, 실제 응답은 `flows-standalone.json`에 기록했으며 운영 적용은 하지 않았다.

## 전달 기준

가장 높은 점수가 0.6 이상이고, 1·2위 점수 차이가 0.2 이상이면 빠른 판정을 사용한다. 둘 중 하나라도 기준에 못 미치면 LLM으로 넘긴다. 기존 운영 기준 그대로이며, 이번 결과로 수치를 조정하지 않았다. 이 점수는 실사용에서 맞을 확률로 보정한 값이 아니다.

0.8B는 `scope` 하나를 JSON으로 선택한다. 모델이 숫자로 낸 확신은 사용하지 않는다. 테스트의 LLM은 로컬 Ollama Qwen3.5 0.8B Q8_0이다. 브라우저의 Q4·kev LoRA 그래프 실행 결과가 아니다.

## 판정 결과

한국어·영어·중국어로 구성된 일반 요청 99개와 부정·정정 요청 36개를 사용했다. 현재 문자 판정기와 0.8B를 조합한 결과다.

| 설정 | 일반 / 99 | 부정·정정 / 36 |
| --- | ---: | ---: |
| 현재 판정기의 1위 선택 | 75 | 20 |
| 낮은 확신 → 이전 정정 예시 12개로 11범위 선택 | 73 | 33 |
| 낮은 확신 → 같은 언어의 15개 예시로 후보 3개 선택 | 81 | 28 |
| 낮은 확신 → 같은 언어의 15개 예시로 11범위 선택 | 82 | 28 |

15개 예시는 원래 학습 자료의 범위별 1개씩 11개, 새 정정 학습 자료의 범위별 1개씩 4개다. 질문의 정답을 보고 고르지 않았다. 부정문 12개만 제공했던 프롬프트의 범위 불균형을 확인하기 위해 전체 범위의 예시를 넣었다. 위 숫자는 기각 전 1위 선택과 LLM 선택을 비교한 범위 판정 수이며, 기존 앱 답변 성공률을 뜻하지 않는다.

모든 정책에서 현재 판정기가 넘긴 질문은 일반 43/99, 부정·정정 29/36이다. 이 비율은 균등하게 구성한 시험 모음의 결과이며 실제 사용자에게 모델이 호출될 비율로 볼 수 없다.

추가로, 후보 3개마다 학습 문장의 TF-IDF 최근접 예시 하나만 제공한 설정도 시험했다. 현재 판정기에서는 일반 80/99, 정정 23/36이었다. 이전 정정 예시 12개를 유지하면서 후보만 3개로 제한하면 77/99, 29/36이었다. 제한한 후보에 정답이 없던 질문은 일반 7/43, 정정 3/29였다. 예를 들어 한국어의 짧은 딜교 순서 질문에서는 콤보가 후보 밖이라 0.8B가 콤보를 고를 수 없었다.

임베딩 판정기도 같은 기준으로 비교했다. 보강 Arctic은 단독 97/99·28/36에서 기존 0.8B 프롬프트를 붙이면 92/99·34/36, 최근접 예시를 준 후보 3개 방식은 92/99·25/36이었다. 보강 E5는 단독 92/99·25/36, 기존 프롬프트를 붙이면 83/99·33/36, 최근접 후보 3개 방식은 87/99·25/36이었다. 확신이 낮다는 이유만으로 기존 프롬프트에 맡기면, 맞던 1위 판단도 바뀔 수 있다.

## 실제 대화

기존 9개 대화, 33턴을 앱의 `answerDialogue`, 계획기, 답변 작성, 대화 저장·복원 코드로 실행했다. 소개·전체 스탯·R·전체 스킬 전환, Q/W/E/R 전환, 콤보·피오라 상대법 대화다. 순서와 기억은 유지하고 요청 판정 부분에만 실험 정책을 주입했다.

| 방식 | 요청 처리 조건 충족 / 33 | 0.8B 호출 |
| --- | ---: | ---: |
| 현재 앱 경로 | 27 | 0 |
| 기존 예시 12개 + 후보 3개 | 27 | 6 |
| 같은 언어 예시 15개 + 후보 3개 | 27 | 6 |
| 같은 언어 예시 15개 + 전체 11범위 | 28 | 6 |

마지막 설정은 영어·중국어의 짧은 딜교 질문을 콤보로 보내 두 답을 고쳤다. 동시에 영어의 R 하나를 묻는 질문을 전체 스킬로 보내, 기존에 맞던 답 하나를 깨뜨렸다. 한국어 딜교는 여전히 스킬 소개로, 중국어의 기본 정보와 스킬 동시 요청은 전체 스탯으로 보냈다.

높은 점수로 틀린 판단은 이 정책에서 모델에게 전달되지 않는다. 한국어의 “기본 능력치는 알았으니 스킬 전체를 듣고 싶어”와 영어의 기본 정보·스킬 동시 요청은 빠른 판정의 오답이 그대로 남았다. 따라서 기각 질문만 모델로 넘기는 정책은 높은 확신의 오류를 해결하는 수단이 아니다.

## 결정

낮은 확신을 LLM으로 넘기는 구조를 후보로 유지한다. 그러나 현재 설정을 기본 운영 경로로 적용할 만큼 실제 대화 개선이 확인되지는 않았다. 분류 점수 상승과 실제 답변 결과를 분리해서 판단해야 한다. 0.8B가 맞던 답을 깨뜨린 결과까지 포함해 운영 적용을 보류한다.

이번에는 동일한 작은 수작업 자료로 프롬프트 구성을 순차 비교했다. 뒤의 설정은 앞선 실패를 보고 구성했으므로 독립적인 일반화 정확도 추정이 아니다. 다중 턴 결과도 오공·피오라 중심의 33턴으로, 전체 대화 품질을 증명하지 않는다. 모바일·브라우저 추론, 다운로드 여부·동의·모델 실패 처리는 운영에 연결하지 않았다.

## 재현

프로젝트 루트에서 실행한다. 앞선 [부정·정정 시험](../negation/README.md)의 임베딩 캐시와 LLM 기록이 필요하다. 새 LLM 호출은 같은 로컬 서버를 사용하므로 명령을 순서대로 실행한다.

```sh
uv run --python 3.13 --with numpy==2.5.3 --with scikit-learn==1.9.1 python scripts/llm/offline-classifier/evaluate-request-hybrid.py
uv run --python 3.13 --with numpy==2.5.3 --with scikit-learn==1.9.1 python scripts/llm/offline-classifier/evaluate-request-hybrid.py --fixed-examples
uv run --python 3.13 --with numpy==2.5.3 --with scikit-learn==1.9.1 python scripts/llm/offline-classifier/evaluate-request-hybrid.py --balanced-examples
uv run --python 3.13 --with numpy==2.5.3 --with scikit-learn==1.9.1 python scripts/llm/offline-classifier/evaluate-request-hybrid.py --balanced-examples --all-scopes
npx tsx scripts/llm/offline-classifier/evaluate-request-hybrid-flow.ts
npx tsx scripts/llm/offline-classifier/evaluate-request-hybrid-flow.ts --balanced-examples
npx tsx scripts/llm/offline-classifier/evaluate-request-hybrid-flow.ts --balanced-examples --all-scopes
uv run --python 3.13 --with numpy==2.5.3 --with scikit-learn==1.9.1 python scripts/llm/offline-classifier/evaluate-request-standalone.py
npx tsx scripts/llm/offline-classifier/evaluate-request-hybrid-flow.ts --llm-only
```

`report.json`은 기존 프롬프트 및 최근접 후보 예시 정책, `fixed-examples.json`은 정정 예시 12개와 후보 제한, `balanced-examples.json`은 같은 언어 예시 15개와 후보 제한, `balanced-all-examples.json`은 같은 예시와 전체 범위 선택 결과다. `flows*.json`에는 실제 답변과 판정, 모델을 호출했는지를 남겼다. LLM 출력 캐시는 모델 digest와 실제 요청 본문을 해시한 키로 저장하며 Git에서 제외한다.

기존 보고서의 소스 해시는 각 시험 당시 버전을 가리킨다. 하이브리드 결과를 기록한 커밋은 `7e442e16d`이며, 단독 모드를 추가한 흐름 스크립트의 해시는 `flows-standalone.json`에 따로 남겼다.
