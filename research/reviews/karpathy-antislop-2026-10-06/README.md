# Karpathy · anti-slop 로컬 점검

최신 상태: 사용자의 B·C·D 승인 뒤 구현과 전체 범위 점검을 진행했다. 현재 적용 결과와 검증은 [APPLIED.md](APPLIED.md)를 확인한다. 아래 내용은 승인 전 점검의 기록이다.

2026-10-06. 앱 시작 오류와 모델 적재 오류를 좁게 수정했고, UI 변경은 적용하지 않은 비포·애프터 시안으로 정리했다.

## 결과와 확인할 곳

- [UI 비교 시안](ui-proposals.html): B 포커스 표시, C 모바일 터치 영역, D 오류 안내. 선택 전에는 앱에 반영하지 않는다.
- [화면 실행 증거](runtime-evidence.json): 70개 화면 조합과 실패·키보드·터치 재현 결과.
- [주석 변경 검증](comment-verification.json): 7개 파일의 실행 JavaScript가 변경 전후 동일하다.
- [시안 검증](proposal-verification.json): 화면 크기, 테마·비교 전환, 이미지 로딩, 선택 문구를 주 에이전트가 확인했다.

수정한 코드의 검증과 화면 점검은 완료했다. 앱의 접근성·오류 복구가 모두 통과한 상태는 아니며, 아래 미해결 항목은 UI 선택과 별도 구현이 필요하다.

## 카파시 가이드라인이 좋은 이유

`karpathy-guidelines`는 추측을 드러내고, 필요한 만큼 구현하고, 수정 범위를 좁히고, 성공 조건을 실행으로 확인하게 한다. 이번 점검에서는 다음과 같이 적용했다.

1. 불확실한 UI 문제를 소스만 보고 확정하지 않고 브라우저에서 재현했다.
2. 실패한 Promise와 저장소 접근이라는 실제 원인을 고쳤다.
3. 줄 수를 맞추기 위한 파일 분할이나 디자인 교체를 하지 않았다.
4. 회귀 테스트, 앱 실행, 기존 화면 테스트로 수정 결과를 확인했다.

## 요구사항 처리

- `karpathy-guidelines`: 코드 오류·복잡도·변경 범위·검증을 점검했다.
- `antislop:antislop-code`: 주석에만 적용했다. 실행 코드 변경은 아래 오류 수정과 별도로 구분했다.
- `antislop:antislop-human`: 키보드, 포커스, 대비, 입력 이름, 오류 인지를 점검했다.
- `antislop:antislop-ui`: 기존 디자인의 목적을 확인하고 기능·상태 문제 위주로 점검했다.
- `antislop:antislop-layoutmobile`: 360·390·768·1024·1440px, 터치, 오버플로, 조작 영역을 점검했다.
- `antislop:antislop`: 이 대화에서 선택한 `during` 모드로 적용했다.
- 사용자의 추가 지시: UI 디자인을 변경하지 않고, 검토할 수 있는 시안을 별도 파일로 만들었다.
- 기존 작업: LLM 평가·프로토콜·생성·LoRA·lockfile 등 이미 수정 중이던 파일을 보존했다. 점검 도중 생긴 다른 작업 파일도 수정하지 않았다.

코드, 주석, 화면 점검을 세 서브에이전트와 나눴으며 최종 실행 확인과 결과 검토는 주 에이전트가 수행했다. `design`, `agent-browser`, `react-best-practices`도 확인에 사용했다. 입력 이름, 네이티브 버튼, 포커스 점검은 [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)와 교차 확인했다.

## 수정한 코드

### P1. sessionStorage 차단이 앱 시작을 막음

위치: `src/data/cache/versionedCache.ts`, `getSessionCacheStorage()`.

브라우저가 `window.sessionStorage` 속성 접근에 `SecurityError`를 던지면 저장소 생성이 모듈 로딩 중 실패했다. 선택적인 캐시 때문에 앱 전체가 시작하지 못하는 문제다.

속성 접근을 보호하고 실패하면 `undefined`를 반환하게 했다. 기존 메모리 캐시는 그대로 동작한다.

검증: 추가한 `tests/unit/session-cache.test.ts`에서 차단된 속성, repository import, 최초 데이터 로딩, 반복 요청의 메모리 캐싱을 확인했다. 브라우저에서도 sessionStorage 접근을 차단한 상태로 VS 화면이 정상 표시되고 실행 오류가 없는 것을 확인했다.

### P2. 모델 적재 실패를 계속 재사용함

위치: `src/workers/advisor/model.ts`, `load()`.

토크나이저나 모델 적재가 실패해도 거절된 `loading` Promise가 남아 이후 `load()`도 같은 실패를 돌려줬다. 실패 시 모델·토크나이저·Promise를 비워 다음 요청에서 다시 적재하게 했다. 재시도 시작 시 이전 파일 진행률도 비운다.

검증: 추가한 `tests/unit/advisor-model-load.test.ts`는 실제 모듈을 SDK 경계만 모킹해 실행한다. 토크나이저 실패, 모델 실패, 다음 요청 성공, 동시 요청의 단일 적재, 성공한 모델의 재사용, 이전 진행률 제거를 확인했다. 실제 모델의 대용량 다운로드와 WebGPU 추론은 실행하지 않았다.

범위: 다음 `load()` 요청이 재시도할 수 있도록 한 수정이다. 자동 재시도나 새 UI 버튼은 추가하지 않았다. `useAdvisor.ensureLoaded()`의 기존 worker 가드는 그대로이므로 재적재 요청을 시작하는 사용자 흐름은 추가 검토 대상으로 남는다.

### lint가 생성된 연구 캐시를 검사함

위치: `eslint.config.js`.

최초 `npm run lint`는 `research/.cache/tuning/` 안의 복제 저장소와 Python 의존성의 JS까지 검사해 오류 88개와 경고 18개를 냈다. 생성된 캐시 경로 `research/.cache/**`만 제외했다. 유지하는 제품·테스트·연구 도구의 lint 규칙은 유지했다.

## 남은 코드 문제

### P2. 이전 패치의 저장된 답이 현재 패치 카드와 섞임

위치: `src/lib/advisor/history.ts`의 `reviveAnswer()`·`reviveTurn()`, `src/components/features/advisor/CompareAnswerCard.tsx`.

저장한 숫자·비교 행·문장은 유지하면서 챔피언 카드만 현재 자료에서 가져온다. 이전 패치의 대화 메모리는 버리지만 답의 수치와 문장은 남으며, 카드 푸터에는 현재 패치를 전달한다.

실제 모듈에 재현용 자료를 넣어 이전 패치의 Q 값 8과 현재 카드의 Q 값 7이 한 답에 함께 남는 것을 확인했다. 이 숫자는 오류 재현을 위한 시험값이다.

권장: 답의 원본 패치를 저장하고 이전 답임을 표시한다. 출처 패치가 없는 과거 저장본은 출처를 알 수 없다고 처리해야 한다. 이미 저장한 대화를 지우거나 현재 답처럼 다시 표시하는 방식은 피한다. 표기와 복원 정책이 함께 필요한 변경이라 이번에는 적용하지 않았다.

### P2. 자료를 못 받으면 저장된 대화 복원이 끝나지 않음

위치: `src/hooks/useAdvisorHistory.ts`, `src/components/features/advisor/AdvisorWidget.tsx`, `AdvisorComposer.tsx`.

저장된 대화가 있으면 `restoring`이 참으로 시작하고 자료가 들어와야 해제된다. 초기 지식 요청의 실패를 위젯이 삼켜 복원 상태가 계속 남는다.

브라우저에서 저장된 대화를 넣고 `advisor-knowledge.json`에 503을 반환했다. 복원 중 안내가 계속 표시되고, 질문을 입력해도 보내기 버튼이 비활성화됐다. 네트워크 차단을 해제하고 패널을 다시 열어도 전송이 막혀 있었다.

권장: 로딩과 실패를 구분하고 저장된 대화를 보존한 채 자료 재시도를 제공한다. 오류 상태가 화면에 추가되므로 UI 변경안과 함께 구현해야 한다.

## UI 점검 결과와 변경 제안

기존 방향은 LoL의 실제 챔피언·스킬 이미지와 수치를 빠르게 견주는 도구다. 표의 정보 밀도, 조용한 배경, 기존 보라색 강조, 라이트·다크 테마를 유지한다. 검토 시안은 ENERGY 1, RHYTHM 1, MOTION 1로 두고 장식이나 자동 애니메이션을 추가하지 않는다.

기존 아이콘은 스킬·챔피언 식별, 강조색은 선택·포커스, 표는 수치 비교, 그림자는 겹친 대화·상세창의 높이 구분을 위한 것이다. 템플릿이라는 이유로 제거하거나 교체할 근거는 없었다.

### 실제로 확인한 문제

1. **모바일 챔피언 탭을 키보드로 선택할 수 없음.** `SortableNormalTab.tsx`의 선택 영역은 클릭하는 div이고 `tabIndex`는 -1이다. 가렌 탭의 포커스 가능한 항목은 드래그·제거뿐이었다. 챔피언 이름 영역을 네이티브 버튼으로 바꾸는 제안을 기록했다.
2. **도우미와 모바일 메뉴의 키보드 수명 주기가 없음.** 도우미를 키보드로 열면 포커스가 BODY로 가고 Escape로 닫히지 않는다. 닫아도 시작 버튼으로 돌아오지 않으며 Tab은 배경 메뉴까지 이동한다. 모바일 메뉴도 Escape로 닫히지 않았다. 기존 모양을 유지하면서 포커스 이동·반환·모바일 가두기·Escape를 구현해야 한다.
3. **포커스 표시가 약함.** 공유 Button의 40% 불투명도 링은 페이지 배경 대비 라이트 약 1.89:1, 다크 약 1.69:1이다. 기존 링 색을 불투명하게 쓰면 약 6.19:1, 4.62:1로 올라간다. 시안 B에서 비교한다.
4. **백과사전 오류가 빈 목록 또는 끝나지 않는 로딩으로 보임.** 정규화 items·runes 요청에 503을 반환하면 `챔피언 목록이 비어있습니다`가 나온다. summoner는 `로딩 중...`에 남는다. 세 경우 모두 처리되지 않은 Promise 오류가 발생하며 재시도 버튼이 없다. 오류 상태 시안 D로 제안한다.
5. **1024px 터치 기기에서 룬 상세를 열 수 없음.** 실제 touch context에서 집중 공격을 탭했지만 dialog와 tooltip이 모두 0개였다. 데스크톱 hover를 유지하면서 모든 폭에서 클릭·탭으로 기존 상세창을 열게 해야 한다.
6. **작은 모바일 조작 영역.** VS 상단 조작 버튼은 높이 32px, 공유 상세창 닫기는 16×16px이다. 시안 C는 선택한 조작 영역만 44×44px로 넓히고 아이콘은 16px로 유지한다. 패치 필터·메뉴 행의 작은 영역도 후속 대상으로 남는다.
7. **검색 입력 이름 누락.** `ItemsTab.tsx`, `SummonerTab.tsx`의 검색 입력에는 placeholder만 있다. 기존 번역을 aria-label로 사용할 수 있다.

소스 색 토큰 계산에서는 라이트 테마의 muted 글자와 muted 배경이 약 4.42:1이고, 글자에 80%·90% 불투명도를 쓰면 배경 대비 약 3.20:1·3.84:1까지 내려간다. 실제 사용하는 표면과 최종 색의 브라우저 확인 없이 전역 색 토큰을 바꾸지는 않았다.

### 선택할 수 있는 시안

- **A. 현행 유지:** 앱의 현재 디자인을 그대로 둔다.
- **B. 포커스 표시:** 기존 색·배치·크기를 유지하고 키보드 포커스 링을 또렷하게 한다. 라이트·다크, 데스크톱·모바일 비교를 제공한다.
- **C. 모바일 조작:** VS 버튼과 상세창 닫기의 터치 영역을 44px로 넓힌다. 일부 행의 높이와 버튼 사이 간격이 늘어나는 차이를 확인할 수 있다.
- **D. 실패 상태:** 빈 목록으로 보이는 오류에 실패 안내와 재시도 위치를 제안한다. before는 실제 앱에 503을 반환해 얻은 화면이고 after는 브라우저에만 만든 미구현 시안이다.

B·C·D는 각각 선택할 수 있다. 시안 페이지의 선택은 검토용이며 앱 소스에 반영되지 않는다. 키보드 동작·복원·패치 표기·검색 이름·태블릿 룬 상세 문제는 위 목록과 별도로 남아 있다.

## 구조와 복잡도

`src`의 TypeScript 파일 360개를 길이와 함수 범위로 검사했다. 400줄 초과 파일 10개, 100줄 초과 함수 28개를 찾았다. JSX와 설명 주석도 포함한 길이이며 오류 개수는 아니다.

가장 긴 파일은 `calculationPartEvaluator.ts` 615줄, `prose.ts` 579줄, `grounding.ts` 573줄이다. `evaluatePart()`는 여러 계산식 종류를 한곳에서 처리한다. 책임별 처리 함수를 분리할 후보지만 종류별 의미와 레벨·랭크 계산 조건을 보존해야 한다. 타입·번역 선언 파일은 응집도가 높으므로 숫자만 맞추는 분할의 이득이 작다.

긴 JSX 함수에는 `SkillsSectionDesktop`, `SkillTooltip`, `ChampionSelector`, `AdvisorPanel`이 포함된다. 화면을 변경하지 않는 별도 리팩터링으로 작은 표시 책임을 분리할 수 있다. 이번 오류 수정과 섞지 않았다. 복잡도 점수와 모든 분기의 최대 중첩 깊이를 정량 측정한 것은 아니다.

## anti-slop Delivery Gate

이 판정은 수정 코드와 검토용 시안의 전달 범위에 대한 것이다. 현재 앱의 미해결 UI 문제를 PASS로 간주하지 않는다. 사용자가 화면 변경 전 시안 선택을 요구했으므로 해당 수정은 적용하지 않았다.

### 1. Hard Gate

- PASS: 실제 앱·기존 게임 자료의 화면을 사용했다. 새 이미지·가상의 후기·지표·고객·게임 수치를 만들지 않았다.
- PASS: 앱의 시각적 마크업·클래스·레이아웃 변경 0개. 주석이 바뀐 화면 파일의 실행 결과도 동일하다.
- PASS: 타입·lint·테스트·빌드·앱 실행을 확인했다. 번들 경고와 UI 실패는 숨기지 않고 기록했다.
- HOLD: 현재 앱의 키보드·오류 복구·태블릿 터치·작은 조작 영역은 선택 후 구현이 필요하다.

### 2. Purpose Gate

- PASS: B는 키보드로 현재 위치를 찾기 위한 표시다. 기존 색을 그대로 쓴다.
- PASS: C는 손가락으로 조작할 영역을 확보한다. 스킬 표·아이콘 크기를 장식 목적으로 변경하지 않는다.
- PASS: D는 실패와 빈 목록을 구분하고 다음 행동의 위치를 보여 준다. 오류 주입과 미구현 시안을 구분한다.
- PASS: 기존 이미지·강조색·표·겹친 창의 그림자는 정보 식별·선택·비교·높이 구분의 역할로 유지했다.

### 3. Liveliness Gate

- PASS: 기존 정보 밀도·게임 이미지·선택 강조를 유지한다. 새로운 템플릿·그라데이션·장식·자동 움직임을 추가하지 않는다.
- PASS: 시안의 ENERGY 1, RHYTHM 1, MOTION 1은 수치를 읽고 조작하는 도구의 목적에 맞는다.

### 4. Craft & Quality Gate

- PASS: 코드 회귀 테스트와 기존 화면 E2E가 통과했다. 정상 화면의 오버플로와 실행 오류를 따로 확인했다.
- PASS: 주석 변경과 실행 코드 변경의 범위를 분리하고 기존 작업을 보존했다.
- PASS: UI 시안은 실제 before와 브라우저에서만 만든 after를 비교한다. 선택만으로 제품을 수정하지 않는다.
- HOLD: 앱 전체의 접근성·실패 복구 검증은 미해결 항목의 구현 이후 다시 필요하다.

다음 행동은 비교 시안에서 B·C·D의 적용 여부를 선택하는 것이다. 저장된 답의 원본 패치와 복원 실패 문제는 별도 후속 수정 항목으로 남는다.
